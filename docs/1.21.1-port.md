# Porting Forbric to Minecraft 1.21.1

Everything below was measured in this repository on 2026-10-20 unless it says otherwise. The point of writing it
down is that most of it contradicts the natural first assumption, and the assumptions cost more time than the
measurements did.

**Status: not ported.** Stages 1-3 are done or nearly done. Stage 4 stops at one root cause that is now proven.

---

## The one fact that explains most of the difficulty

**26.2 is unobfuscated (Mojmap-native). 1.21.1 is obfuscated.**

Forbric was built against 26.2 first, so a whole set of code paths that only matter on an obfuscated game has never
executed. They are not "buggy on 1.21.1"; they were never exercised at all. Four separate problems reduce to this:

| Where | What is wrong on 1.21.1 | Why 26.2 hid it |
|---|---|---|
| `KernelMappingResolver` | all six methods `return input;` | identity mapping is correct when obf-id == named-id |
| `KernelMixinBootstrap` | `REQUIRED_JAVA_FEATURE = 25` | 26.2 really is class-file 69 |
| `ForgeTransferShapeAudit` | 8 audited SHA-256 fingerprints are 26.2's | the classes are 26.2's Forge classes |
| `PatchedMcBuilder` | applies Forge binpatches to the obfuscated jar | on 26.2 the obfuscated jar *is* the Mojmap jar |

If a claim about 1.21.1 has no measurement behind it, the safe prior is that it is the 26.2 answer wearing a
different version number.

## Stage 1 - namespace mapping: DONE

Required because 1.21.1 fabric-api is built against intermediary names. Measured counts:

```
fabric-api 0.116.17+1.21.1   class_ 19,859   method_ 1,729   field_ 862   (48 of 49 modules)
fabric-api 0.161.0+26.2      class_      0   method_     1   field_   0
```

Chain for 1.21.1: obfuscated <-> intermediary <-> Mojmap. That needs a JOIN of two mapping files, because neither
side names all three.

What is in the tree and works:

- `tools/namespace/join-mappings.ps1` - class-level join (intermediary + Mojang client mappings -> Mojmap).
  Asserts against a real merged base: **8 of 8 probes PRESENT**.
- `tools/namespace/join-members.ps1` - member-level join, with field and method as separate dimensions.
  **77,152 of 78,922 = 97.7%**. Four mapped member names confirmed by `javap` against real bytecode.
- `tools/namespace/emit-table.ps1` - emits `mappings-1.21.1.tsv` (5,077,063 bytes).
- `KernelMappingResolver` reads a pre-joined table from `-Dforbric.mappings=<file>`; identity when absent, which is
  the 26.2 path. `KernelMappingResolverTableTest` 6/0, existing `KernelMappingResolverTest` 3/0.

Mapping-format traps, all of which produced a silent zero or a wrong name rather than an error:

- tiny member lines are `\t<marker>\t<descriptor>\t<obf>\t<intermediary>` - field 2 is the DESCRIPTOR, not a name.
- Mojang's `client.txt` is `<mojmap> -> <obf>:`, i.e. reversed relative to what you expect.
- `# {...}` annotation lines reset the current owner if not skipped.
- Field and method must be a key dimension: obf names are shared across them (`field_18276` came out as a method).
- Path separators: `.` vs `/`.

## Stage 2 - Java version: DONE

`REQUIRED_JAVA_FEATURE = 25` became `requiredJavaFeature()`, which reads the class-file major from the game's own
`ItemStack.class` (bytes 6-7, feature = major - 44), validates `CAFEBABE`, and returns **0 for "no opinion"** on a
probe failure rather than claiming Java 0.

Measured: 26.2 `ItemStack.class` major 69; both 1.21.1 bases major 65.

`ForbricMixinService` used to clamp `CompatibilityLevel` down to `getCompatibilityLevel()`, which turned 60 fabric
configs into `JAVA_8` and produced `Unsupported registry: minecraft:block`. It now clamps only to `MAX_SUPPORTED`.

Test evidence: mixin + mapping suites 1769 cases, 24 failures, all of them Windows TempDir deletion (a known
limitation). Real failures: 0.

`tools/dev.py` derives its Java minimum from the version now, and this was verified on the real command path:
`FORBRIC_MC_VERSION=1.21.1` reports "JDK 21+ required" and 26.2 reports "JDK 25+ required", and
`compileToolsJava`/`mergeToolsJar` succeed under JDK 21.

## Stage 3 - bytecode fingerprints: 1 of 19 assessed

`ForgeTransferShapeAudit` pins a SHA-256 of seven Forge/NeoForge classes and refuses transfer writes for any shape
it has not reviewed. `tools/fingerprint/` reproduces that hash standalone, without a running kernel.

**The self-check is the only reason its output is usable:** run against 26.2's `forge-runtime.jar` it must reproduce
the pinned values. Measured: **7 of 7 reproduced, 0 mismatches.** Only after that did the 1.21.1 numbers mean
anything - one skipped step in the normalisation chain gives a different hash and the difference is invisible.

Measured on 1.21.1 (`merged-1.21.1-collect.jar`): all six present classes differ. The seventh is the finding:

```
Forge 1.21.1 CapabilityProvider inner classes:  2   (CapabilityProvider, $AsField)
Forge 26.2    CapabilityProvider inner classes:  7   (+ $AsField$LevelChunks, $BlockEntities,
                                                       $Entities, $ItemStacks, $Levels)
```

So the audit's premise - that an ItemStack's capability provider is the `$ItemStacks` inner class - does not hold on
1.21.1. Re-pinning hashes cannot fix that; the audit needs reasoning about per version.

The other 18 fingerprint sites are **not assessed**.

## Stage 4 - build and launch: blocked at one proven root cause

### The pipeline, which is not where you would look

The staged artifacts are produced by **the installer jar**, not by the shell scripts:

```
java -jar <installer> --dir <instance> --mc <version>
```

- `ArtifactBuilder.build(mcDir, mcVersion, jvm)` is already version-parametric; it resolves vanilla from
  `mcDir/versions/<mcVersion>/<mcVersion>.jar` and produces all six artifacts.
- `Pins.java` is what locked the version: `MINECRAFT`, `FORGE`, `NEOFORGE`, `NFRT`, `NFRT_RESULT`.
  All three version pins now read a system property and default to their 26.2 values.
- `Pins.stamp()` composes the whole set into one line and that line is the artifact cache key, so a half-changed pin
  set is safe rather than silently wrong: the stamps stop matching and everything rebuilds.
- `forbric-loader/run/build-merged-base.sh` is a development side path. Its own comment says the kernel owns the
  tools and "this project keeps no copy that could drift from it" - the real source is
  `forbric-kernel/src/tools/`, which is a **different file** (1917 lines) from the one under `.firstgen-backup`
  (1945 lines). Use the former.
- `.pins` files in `.forbric-build/out/` split into two different `tools=` hashes, so those artifacts came from two
  different installer builds. There is no `provenance.json`.

### The root cause

Running the pipeline with `-Dforbric.pin.minecraft=1.21.1 -Dforbric.pin.forge=1.21.1-52.1.20` gets all the way to
`binarypatcher` and fails:

```
Patch expected net/minecraft/server/Main$1 to have the checksum f734ba89 but it was e6be7ea9
```

Disassembling the same class from both sides settles it:

```
Forge official output (patched-mc-forge-1.21.1.jar)   Main$1  942 bytes
  final net.minecraft.server.MinecraftServer val$dedicatedserver;      <- Mojmap
  instanceof net.minecraft.gametest.framework.GameTestServer           <- Mojmap

PatchedMcBuilder's clean.jar                          Main$1  644 bytes
  final apn a;                                                        <- obfuscated
  invokevirtual apn.a:(Z)V                                            <- obfuscated
```

**Forge's binpatches are built against the DEOBFUSCATED jar. `PatchedMcBuilder` applies them to the obfuscated one.**
Its nine steps are: BUNDLER_EXTRACT, mergetool `--merge --ann API`, extract binpatches, binarypatcher, overlay,
access transformers, covariant self(). **There is no deobfuscation step, and no renaming step either** - an earlier
guess that `ForgeAutoRenamingTool --reverse` was a no-op on 26.2 was wrong; that tool does not appear in this file.

No SRG mappings are available anywhere in this tree or in the userdev jar (`forge-userdev.jar` holds only
`config.json`, `joined.lzma`, and `patches/*.java.patch`), so adding the missing step means obtaining mappings.
Mojang's own `client-1.21.1.txt` is already present under `namespace-probe/`.

### What is already correct, and can be used as-is

Naming shapes measured across the whole jars:

```
forge-probe-1211/patched-mc-forge-1.21.1.jar              9,478 classes   obfuscated short names: 0
nfrt-probe-1211/.../neoforge-21.1.249-merged.jar          9,768 classes   obfuscated short names: 0
forbric-kernel/.dev/minecraft/versions/1.21.1/1.21.1.jar  8,269 classes   obfuscated short names: 5,344
```

Both patched bases are **pure Mojmap**, which is exactly what `MergedBaseBuilder` expects. The vanilla client is not,
which is the one piece missing for the shortcut path below.

### Two ways forward

**A. Shortcut (unproven).** Deobfuscate the 1.21.1 vanilla with the Mojang mappings already in the tree, then feed
all three Mojmap jars to `MergedBaseBuilder`. Gets a launch attempt without touching `PatchedMcBuilder`. It is a
WORKAROUND, and it leaves the build pipeline still unable to produce a 1.21.1 base on its own.

**B. Correct fix (unproven).** Add the deobfuscation step to `PatchedMcBuilder` so the Forge side is built the way
Forge builds it. Requires mappings and touches the build path shared with 26.2, so it needs the 26.2 baseline
re-verified afterwards.

Note from stage 0: a `CONFLICTS: methods 1036` figure for 1.21.1 versus `1119` for 26.2 **was reported earlier and is
withdrawn**. Both runs used inputs that do not reproduce the shipped base, and the 1.21.1 run used the wrong tool
copy, so the comparison had no baseline. Do not reuse those numbers.

The last row is what `dev.py prepare` downloads, and it is **not** what a merge wants. The first three are. So the
shortcut needs no remapping at all - it needs the right vanilla file, which already exists on this machine.

## The conflicts, measured comparably

Same tool (`forbric-kernel/src/tools`, including the collect-mode patch), same mode, both sides pure Mojmap. **The
line that matters is the second one, not the `CONFLICT-COLLECTED` count** - a mistake worth recording because it was
made three times:

```
1.21.1  [merge] classes: vanilla=2 forge-only-ns=1200 forge=97 neo=9077 MERGED=600 (superclass-rebased-to-forge=1)
1.21.1  [merge] CONFLICTS: methods=1029 fields=2 STRUCTURAL(superclass/field)=26 collision-methods-dropped=2

26.2    [merge] classes: vanilla=0 forge-only-ns=3 forge=185 neo=10155 MERGED=628 (superclass-rebased-to-forge=2)
26.2    [merge] CONFLICTS: methods=1117 fields=8 STRUCTURAL(superclass/field)=27 collision-methods-dropped=3
```

Read those fields correctly:

- `CONFLICT-COLLECTED #N` lines are only the cases that **threw** in default mode and were caught by collect mode.
  On 1.21.1 that is 4 lines. It is **not** the conflict count.
- `CONFLICTS: methods=...` is the real count. `vanilla=2` means "only 2 classes came from vanilla alone", not "only 2
  vanilla classes were seen" - most classes come wholesale from one of the two patched jars.
- `MERGED=600` is how many classes existed on **both** sides and therefore needed actual merging.

**On every conflict metric 1.21.1 is slightly better than 26.2**, not worse:

```
                   1.21.1   26.2
methods              1029    1117
fields                  2       8
STRUCTURAL             26      27
MERGED                600     628
```

This is consistent with the `1036 vs 1119` figure that an earlier revision of this document withdrew. **That
withdrawal was itself the error**: the number had been produced with the wrong tool copy and unverifiable inputs, so
re-measuring was right, but the conclusion drawn from that ("the figure was meaningless") was not - the figure was
essentially correct and it is now reproduced from a run whose inputs are two pure-Mojmap patched jars.

## The real extra cost is `forge-only-ns`

```
1.21.1   1,200
26.2         3
```

That is a difference of about 1,197 classes: classes that exist only in Forge's namespace. 26.2 needs essentially
none of them. **This is more likely to be what actually costs work on 1.21.1 than the conflict counts are**, and it
had not been looked at before it showed up in the same report line that carried the conflict numbers.


## Why conflict #1 cannot be fixed by relaxing a check

`Entity.getMaxHeightFluidType()` exists in both patched jars with identical arguments and different return types:

```
Forge      public net.minecraftforge.fluids.FluidType        getMaxHeightFluidType()
NeoForge   public net.neoforged.neoforge.fluids.FluidType    getMaxHeightFluidType()
```

Neither `FluidType` is an ancestor of the other - they are two unrelated classes with the same simple name.

The throw comes from one place, `MergedBaseBuilder.java:1024`, inside the `bm == null` branch. That branch already
recognises the situation (its comment says these are the same conceptual method, retyped by each compiler to its own
extension type, and that it should "reconcile to whichever ancestor we ACTUALLY chose") but **the reconciliation is
not implemented**: `boolean handled = false;` is never assigned `true`, so the only outcomes are the throw or a
straight splice.

`compatibleReturnContracts` (line 599) is **not** the bug. It accepts only one narrow shape: every `ARETURN` must be
preceded by a read of a field of the owner class, whose type is assignable to the return type - i.e. a cached-field
accessor. `getMaxHeightFluidType()` walks a map to find the highest entry, so it is correctly rejected.

Which means fixing this requires a **design decision**, not a code fix: on 1.21.1, which `FluidType` should the merged
`Entity` expose, or does it need a bridging class? That decides which ecosystem's mods work, and it is a question
about Forbric's intent rather than about the merge tool.

`ChunkGenerator` ("Incompatible initializer dependency") and `ItemBlockRenderTypes` ("retyped return") are separate
branches and have not been examined.

## 26.2 still cannot be reproduced here

Recorded because it keeps being assumed otherwise: running the active tool on 26.2 in **default** mode aborts on
`ReloadableServerResources#getConditionalServerResources` and produces nothing. Collect mode succeeds with 2
conflicts. So a shipped 26.2 merged base exists that this machine cannot regenerate through that path, and any

# DANGER: `dev.py prepare` for 1.21.1 overwrites 26.2's state

`ArtifactBuilder.build()` writes `.dev/minecraft/.forbric-build/out/forge-runtime.jar` **first**, at
`ArtifactBuilder.java:101`, before the merge and before the `binarypatcher` step that currently fails. That filename
carries no version, so both lines share it. **A 1.21.1 `prepare` run therefore replaces the 26.2 Forge carrier on its
way to failing**, and the failure means nothing regenerates it.

Anyone touching this should either back that file up first, or make the path version-qualified before running prepare
for a second version. This is recorded here because it was found by a subagent reading `ArtifactBuilder`, not by
running into it - and earlier rounds of this port did run 1.21.1 prepares, so the 26.2 carrier may already have been
overwritten on this machine.

# The real size of the port: 151 runtime sources, 810 compile errors

An earlier revision of this document said the 26.2 audit found "about 15 lines to rewrite". **That estimate was wrong
by roughly fifty times**, and the reason is worth keeping: it was based on how few places name the version string.
Naming a version and depending on a version's API are different questions, and the kernel does the second one
constantly.

Measured by compiling the kernel's runtime source set against staged 1.21.1 artifacts:

```
810 errors across 151 runtime sources
```

Roughly a hundred corners of it, along three independent version axes:

| Axis | What is gone | Example |
|---|---|---|
| **Minecraft 26.x -> 1.21.1** | classes renamed between the versions | `net/minecraft/resources/Identifier` is gone; 1.21.1 has `ResourceLocation`. **101 uses.** Also `PackFormat`, `FuelValues`, `TooltipDisplay`, `EntitySpawnReason`, `SubmitNodeCollector`. |
| **Forge/NeoForge 26.x -> 1.21.1** | EventBus 7 API vs 6.2.33 | `eventbus.api.bus.EventBus<T>`, `BusGroup`, `listener.SubscribeEvent` do not exist; 1.21.1 ships `IEventBus`. Also `neoforgespi.transformation.*` and `fml.classloading.transformation.*`. |
| **fabric-api transfer 0.155 -> 0.116** | the API was renamed | `ItemVariant`/`FluidVariant`/`Storage` are 26.2 names; 1.21.1 has `ItemResource`/`FluidResource`/`TransactionContext`, plus `ResourceHandler`, `EnergyHandler`, `Operation`. |

This is **not** a staging hole, and that was checked in both directions: `ResourceLocation` and `FMLPaths` are present
in the staged jars, so the classpath resolves, and the missing symbols are genuinely absent from 1.21.1.

## What assembling the artifacts did teach

Nine of the eleven staged artifacts can be produced from what is on this machine. The two that cannot are the canary
mods, whose sources do not compile against 1.21.1 for the same reasons as the kernel.

The stock `assemble-*.sh` scripts **hardcode 26.2 auxiliary library versions**. 1.21.1's FML wants eventbus 6.2.33 and
forgespi 7.1.5 where 26.2 wants 7.0.1 and 8.0.0; mixing them assembles cleanly and fails later. Versions have to come
from each line's own userdev `config.json`, not from those scripts.

50 of 1.21.1's 54 Minecraft libraries are absent from `.dev/minecraft/libraries`, which holds 26.2's versions, so
`ready()` stays false until `stage_minecraft()` runs for 1.21.1.

## So what remains

Porting 151 runtime sources along three API axes. That is the whole of stage 4. Nothing about launching can be
measured until it is done, because no kernel jar exists to launch.

## The names are mutually exclusive, so there is no rename

Every symbol on this axis is present on exactly one line:

```
net.minecraft.resources.Identifier         26.2=PRESENT  1.21.1=absent
net.minecraft.resources.ResourceLocation   26.2=absent   1.21.1=PRESENT
```

Same shape for `EntitySpawnReason`/`MobSpawnType`, `EntityTypes`/`EntityType`,
`WeightedList`/`WeightedRandomList`, `AbstractBoat`/`Boat`, `TriState`, `Hud`, `ValueInput`. So a blanket
rename cannot work: whichever spelling the sources use, the other line stops compiling. And 118 of the 136
`Identifier` occurrences are **type positions** (declarations, generics, `.class` literals), which no wrapper or
helper can absorb, because every vanilla call takes and returns the real type.

## The mechanism: a declared rename table, applied at build time

`forbric-kernel/src/runtime/mc-line/1.21.1.tsv` holds `<26.2 name> TAB <1.21.1 name>`. The Gradle task
`normalizeRuntimeJava` copies `src/runtime/java` into `build/generated/mc-line/<line>/java`, applying the table
whole-token and longest-name-first, and the runtime source dir is pointed at that copy. This is the compile-time
twin of what `ForbricMappings` already does to bytecode at runtime.

**On 26.2 nothing happens.** The task, the `srcDir` swap and the dependency are all inside
`if (mcLine != '26.2')`, so a default build's source dir is still `src/runtime/java` and no extra task joins the
graph. The line is chosen by `-Pforbric.mcLine`, then `FORBRIC_MC_VERSION` (the variable `tools/dev.py` already
reads), then 26.2.

Two guards, both exercised rather than assumed:

- a rule that matches nothing **fails the build** (a stale entry would otherwise become a compile error on the
  other line, which reads as an engine difference);
- a line with no table **fails naming the file**, never silently building as 26.2.

The table is names only. Member-level counterparts that change the *shape* of an expression
(`Minecraft.gui.setScreen` -> `Minecraft.setScreen`, `WorldVersion.packVersion():PackFormat` ->
`getPackVersion():int`, `Gui.overlay()`) are written down in the table's tail as facts, not as rules.

Measured absent from 1.21.1 with no same-named equivalent, so these need restructuring that also has to keep 26.2
correct — which is why they are **not** table entries:

`TooltipDisplay` (no pre-1.21.2 tooltip-display component) · `FuelValues` · `PackFormat` (int before 1.21.9) ·

## Axis 2: what was a rename, and what was not

The one thing on this axis that a name table can express is EventBus 7's per-event static bus. 6.2.33 has no
such field; on 1.21.1 every one of those events is posted on the single game bus, whose declaration was read
from the staged 1.21.1 `forge-runtime.jar`:

```
public static final net.minecraftforge.eventbus.api.IEventBus EVENT_BUS;   (net.minecraftforge.common.MinecraftForge)
```

26 rules `X.BUS` -> `net.minecraftforge.common.MinecraftForge.EVENT_BUS` are now in the table, one per event
class, and they account for **26 of the 26 errors removed** (164 -> 138, exactly one per rule).

The interesting part is the six sites that look identical and got no rule:

- `SpawnPlacementRegisterEvent.BUS` and `RegisterClientReloadListenersEvent.BUS` both implement
  `net.minecraftforge.fml.event.IModBusEvent` (javap). They fire on the **mod** bus, which has no name at all
  in 6.2.33 — it is reached through `FMLJavaModLoadingContext.get().getModEventBus()`, an expression. A rule
  would compile and silently deliver the event to nobody.
- `EntityEvent.EnteringSection.BUS` and `LivingEvent.LivingVisibilityEvent.BUS` are called as
  `.BUS.hasListeners()`, and `IEventBus` in 6.2.33 has no `hasListeners()` at all (javap: register,
  addListener x4, addGenericListener x4, unregister, post x2, fire x2, shutdown, start). Rewriting the
  receiver would trade one error for another and *move it out of this axis's count*, which is not a fix.
- `AttachCapabilitiesEvent.{Levels,Entities,BlockEntities}.BUS` — those inner classes do not exist on 1.21.1,
  which is the same 26.x capability-provider split already recorded in stage 3 above.

- **`BreakBlockEvent` really is a rename.** `net.neoforged.neoforge.event.level.block.BreakBlockEvent` (26.2)

<JDK21>/bin/javac -J-Duser.language=en -J-Duser.country=US -J-Dstdout.encoding=UTF-8 \

Two measurement traps found here, both of which produce a silently wrong number rather than an error:

- **javac localises its diagnostics.** On this machine, with no locale pin, a JDK-21 javac emitted
  **GBK-encoded Chinese**, in which `axis-split.py`'s `symbol:` and `package ... does not exist` anchors do not
  exist and the split reported `TOTAL: 0` for a run that had 608 errors in it. The English + UTF-8 pin above
  is what makes the numbers comparable with the ones already in this document.
- `build/x11/classes/` is javac's `-d` target. Without one, javac writes class files next to the generated
  sources and the next `normalizeRuntimeJava` `Sync` deletes them mid-run.

# The fabric-api modules, remapped out of intermediary: 582 -> 571

The previous round recorded, with evidence and deliberately without a fix, that the 1.21.1 fabric-api modules
are **intermediary-remapped** (`class_1263`, `class_2350`, ...) and that this was the reason
`ContainerStorage` -> `InventoryStorage` could not be a rule. Both halves of that are now addressed: the modules
are rewritten to Mojmap at build time on the 1.21.1 line only, and the rule is a rule.

## What was remapped, and the modules that needed it - verified, not assumed

Measured over the three modules `extractTransferApis` pulls out of `fabric-api-0.116.17+1.21.1.jar`, counting
constant-pool references that point into `net/minecraft/`:

| module | class files | files naming net.minecraft | Minecraft classes (distinct) | member refs (distinct) |
|---|---|---|---|---|
| fabric-api-base | 14 | 5 | 1 | 3 |
| fabric-api-lookup-api-v1 | 29 | 19 | 15 | 23 |
| fabric-transfer-api-v1 | 115 | 70 | 88 | 232 |
| the three together | 158 | 94 | **93** | **244** |

All three need it; the previous round's three-module guess was right. The whole affected surface is **93 distinct
Minecraft classes and 244 member references** (the per-module columns overlap; the last row is the union) -
small enough to enumerate, which is why the failure was measurable at all rather than diffuse.

The remap is `remapTransferApis` in `forbric-kernel/build.gradle`, registered only inside the existing
`if (mcLine != mcLineDefault)` guard, so the 26.2 build graph does not gain a task (verified: `--dry-run` of
`compileRuntimeJava` on 26.2 lists neither `normalizeRuntimeJava` nor `remapTransferApis`). It runs
`net.forbric.nsremap.NamespaceRemapper` (ASM 9.10.1 `ClassRemapper` + a hierarchy-walking `Remapper`) over
`build/transfer-api-compile/` and writes `build/transfer-api-mc/1.21.1/`. The runtime source set compiles
against the latter on that line and against the former on 26.2 - one variable, chosen by `mcLine`.

Three things it does beyond a `SimpleRemapper`:

- **Hierarchy walking.** A call site's owner is the static receiver type, not the declaring class.
  `class_1657.method_23317` is declared on `class_1297`; **38 of the 244 references resolve only through a
  supertype.** It also matters for declarations: `AbstractFurnaceBlockEntityMixin` extends a Minecraft class, so
  its own overriding declarations must be renamed with their target.
- **Entry names, not only bytes.** Output entry names come from the same name function, so an inner class moves
  with its outer (`class_2350$class_2351` -> `Direction$Axis` in both places). **No class in these three modules
  is Minecraft-named**, so the real run renames zero entries - the path is proved by a `--selftest` mode that
  builds a jar holding `net/minecraft/class_1799` and its inner class, remaps it, and asserts the entry names,
  the field descriptor and the method names moved (`SELFTEST PASS`, 2 of 2 entries renamed).
- **A verification pass against a real Mojmap jar.** Every class, descriptor, signature, annotation type, LDC
  type and member reference in the OUTPUT is resolved against the staged merged base, walking supertypes, and
  the task fails if one does not. Result: **742 references checked (275 class, 145 field, 322 method), 0
  unresolvable**; 1 member unchecked because its owner chain leaves the base (`Container.toString()`, inherited
  from `java/lang/Object`), and 87 non-Minecraft owners (other fabric modules, guava) which the remap does not
  touch. The remap itself is deterministic: two runs over the same inputs produce byte-identical jars, because
  the entry timestamps are fixed.

The table is `src/runtime/mc-line/1.21.1-fabric-ns.tsv` - a declared, reviewable file, like the rename table,
not something inferred inside a task. It covers the **closure** the modules need: 175 classes and 10,352
members, supertypes included. A name it lacks is reported by the task and fails the build.

## The join behind that table is not the one `emit-table.ps1` does, and the difference is a defect

`tools/namespace/emit-table.ps1` keys members by `(obfOwner, kind, obfName)`. That key is **lossy**: one
obfuscated class reuses a short obf name for many methods that differ only in descriptor - `bsr.a` alone covers
81 - so **8,744 of 70,511 obf keys in `client-1.21.1.txt` carry more than one Mojmap name**, and whichever the
join saw last wins. `tools/namespace/join-keyed.py` adds the descriptor *and* the obf member name to the key:

```
78,922 of 78,922 members joined (100.0%), 0 ambiguous       join-keyed.py
77,152 of 78,922 members joined ( 97.7%)                    the shipped pipeline
```

Two further traps had to be fixed to get there, both silent: **client.txt's obf column is a DOTTED class name**
for the 34 classes Minecraft does not obfuscate (`net.minecraft.server.MinecraftServer`), while tiny writes the
same class slashed - 454 members; and the `10:10:` line-range prefix on client.txt method lines must be stripped
before anything else, or the return type parses as `911:911:boolean` and 40,686 of 41,243 methods join with
nothing.

**This is not only a build-time matter.** `KernelMappingResolver` reads exactly the `C/M/F` format
`emit-table.ps1` writes, so the shipped runtime table carries the same defect. Measured against the merged base:

| property | shipped table | descriptor-keyed table |
|---|---|---|
| member records | 77,152 | 78,922 |
| records where the two tables disagree on the name | 27,074 | - |
| of those, the other table's name is the one present at that owner+signature | 11 | 22,410 |
| two intermediary members mapped onto ONE Mojmap member | **4,025 targets / 8,241 records** | **0** |

A correct join is one-to-one onto Mojmap's member set, so 4,025 colliding targets are impossible rather than
merely unlikely. The corrected full table is one command
(`python tools/namespace/join-keyed.py <out> --full`); it is **not** wired in here, because swapping the runtime
mapping table is a behaviour change on this line and belongs to its own change.
