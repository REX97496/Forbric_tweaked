# Porting Forbric to Minecraft 1.21.1

Everything below was measured in this repository on 2026-10-20 unless it says otherwise. The point of writing it
down is that most of it contradicts the natural first assumption, and the assumptions cost more time than the
measurements did.

**Status: not ported, and no longer blocked at definition.** Stages 1-4 are done. Stage 4's launch blocker — the
loader refusing to *define* `Entity`, `Level` and `BlockEntity` on this line — is removed and proved against the real
base (see "Stage 4: the 1.21.1 certificate" at the end). What remains is the rest of the runtime source set, which
still does not compile on 1.21.1, and everything about launching it.

---

## The one fact that explains most of the difficulty

**26.2 is unobfuscated (Mojmap-native). 1.21.1 is obfuscated.**

Forbric was built against 26.2 first, so a whole set of code paths that only matter on an obfuscated game has never
executed. They are not "buggy on 1.21.1"; they were never exercised at all. Four separate problems reduce to this:

| Where | What is wrong on 1.21.1 | Why 26.2 hid it |
|---|---|---|
| `KernelMappingResolver` | all six methods `return input;` | identity mapping is correct when obf-id == named-id |
| `KernelMixinBootstrap` | `REQUIRED_JAVA_FEATURE = 25` | 26.2 really is class-file 69 |
| `ForgeTransferShapeAudit` | 8 audited SHA-256 fingerprints are 26.2's | the classes are 26.2's Forge classes |
| `PatchedMcBuilder` | applies Forge binpatches to the obfuscated jar | on 26.2 the obfuscated jar *is* the Mojmap jar |

If a claim about 1.21.1 has no measurement behind it, the safe prior is that it is the 26.2 answer wearing a
different version number.

## Stage 1 - namespace mapping: DONE

Required because 1.21.1 fabric-api is built against intermediary names. Measured counts:

```
fabric-api 0.116.17+1.21.1   class_ 19,859   method_ 1,729   field_ 862   (48 of 49 modules)
fabric-api 0.161.0+26.2      class_      0   method_     1   field_   0
```

Chain for 1.21.1: obfuscated <-> intermediary <-> Mojmap. That needs a JOIN of two mapping files, because neither
side names all three.

What is in the tree and works:

- `tools/namespace/join-mappings.ps1` - class-level join (intermediary + Mojang client mappings -> Mojmap).
  Asserts against a real merged base: **8 of 8 probes PRESENT**.
- `tools/namespace/join-members.ps1` - member-level join, with field and method as separate dimensions.
  **77,152 of 78,922 = 97.7%**. Four mapped member names confirmed by `javap` against real bytecode.
- `tools/namespace/emit-table.ps1` - emits `mappings-1.21.1.tsv` (5,077,063 bytes). **Retired as the runtime
  producer**: the table `KernelMappingResolver` reads is now written by `join-keyed.py --full`. See "The runtime
  mapping table, replaced" at the end of this document for the measurement that forced it.
- `KernelMappingResolver` reads a pre-joined table from `-Dforbric.mappings=<file>`; identity when absent, which is
  the 26.2 path. `KernelMappingResolverTableTest` 6/0, existing `KernelMappingResolverTest` 3/0. (Now 9/0 and 3/0:
  the three added tests cover the table's class-name format and a refused truncated record.)

Mapping-format traps, all of which produced a silent zero or a wrong name rather than an error:

- tiny member lines are `\t<marker>\t<descriptor>\t<obf>\t<intermediary>` - field 2 is the DESCRIPTOR, not a name.
- Mojang's `client.txt` is `<mojmap> -> <obf>:`, i.e. reversed relative to what you expect.
- `# {...}` annotation lines reset the current owner if not skipped.
- Field and method must be a key dimension: obf names are shared across them (`field_18276` came out as a method).
- Path separators: `.` vs `/`.

## Stage 2 - Java version: DONE

`REQUIRED_JAVA_FEATURE = 25` became `requiredJavaFeature()`, which reads the class-file major from the game's own
`ItemStack.class` (bytes 6-7, feature = major - 44), validates `CAFEBABE`, and returns **0 for "no opinion"** on a
probe failure rather than claiming Java 0.

Measured: 26.2 `ItemStack.class` major 69; both 1.21.1 bases major 65.

`ForbricMixinService` used to clamp `CompatibilityLevel` down to `getCompatibilityLevel()`, which turned 60 fabric
configs into `JAVA_8` and produced `Unsupported registry: minecraft:block`. It now clamps only to `MAX_SUPPORTED`.

Test evidence: mixin + mapping suites 1769 cases, 24 failures, all of them Windows TempDir deletion (a known
limitation). Real failures: 0.

`tools/dev.py` derives its Java minimum from the version now, and this was verified on the real command path:
`FORBRIC_MC_VERSION=1.21.1` reports "JDK 21+ required" and 26.2 reports "JDK 25+ required", and
`compileToolsJava`/`mergeToolsJar` succeed under JDK 21.

## Stage 3 - bytecode fingerprints: 1 of 19 assessed

`ForgeTransferShapeAudit` pins a SHA-256 of seven Forge/NeoForge classes and refuses transfer writes for any shape
it has not reviewed. `tools/fingerprint/` reproduces that hash standalone, without a running kernel.

**The self-check is the only reason its output is usable:** run against 26.2's `forge-runtime.jar` it must reproduce
the pinned values. Measured: **7 of 7 reproduced, 0 mismatches.** Only after that did the 1.21.1 numbers mean
anything - one skipped step in the normalisation chain gives a different hash and the difference is invisible.

Measured on 1.21.1 (`merged-1.21.1-collect.jar`): all six present classes differ. The seventh is the finding:

```
Forge 1.21.1 CapabilityProvider inner classes:  2   (CapabilityProvider, $AsField)
Forge 26.2    CapabilityProvider inner classes:  7   (+ $AsField$LevelChunks, $BlockEntities,
                                                       $Entities, $ItemStacks, $Levels)
```

So the audit's premise - that an ItemStack's capability provider is the `$ItemStacks` inner class - does not hold on
1.21.1. Re-pinning hashes cannot fix that; the audit needs reasoning about per version.

The other 18 fingerprint sites are **not assessed**.

## Stage 4 - build and launch: blocked at one proven root cause

### The pipeline, which is not where you would look

The staged artifacts are produced by **the installer jar**, not by the shell scripts:

```
java -jar <installer> --dir <instance> --mc <version>
```

- `ArtifactBuilder.build(mcDir, mcVersion, jvm)` is already version-parametric; it resolves vanilla from
  `mcDir/versions/<mcVersion>/<mcVersion>.jar` and produces all six artifacts.
- `Pins.java` is what locked the version: `MINECRAFT`, `FORGE`, `NEOFORGE`, `NFRT`, `NFRT_RESULT`.
  All three version pins now read a system property and default to their 26.2 values.
- `Pins.stamp()` composes the whole set into one line and that line is the artifact cache key, so a half-changed pin
  set is safe rather than silently wrong: the stamps stop matching and everything rebuilds.
- `forbric-loader/run/build-merged-base.sh` is a development side path. Its own comment says the kernel owns the
  tools and "this project keeps no copy that could drift from it" - the real source is
  `forbric-kernel/src/tools/`, which is a **different file** (1917 lines) from the one under `.firstgen-backup`
  (1945 lines). Use the former.
- `.pins` files in `.forbric-build/out/` split into two different `tools=` hashes, so those artifacts came from two
  different installer builds. There is no `provenance.json`.

### The root cause

Running the pipeline with `-Dforbric.pin.minecraft=1.21.1 -Dforbric.pin.forge=1.21.1-52.1.20` gets all the way to
`binarypatcher` and fails:

```
Patch expected net/minecraft/server/Main$1 to have the checksum f734ba89 but it was e6be7ea9
```

Disassembling the same class from both sides settles it:

```
Forge official output (patched-mc-forge-1.21.1.jar)   Main$1  942 bytes
  final net.minecraft.server.MinecraftServer val$dedicatedserver;      <- Mojmap
  instanceof net.minecraft.gametest.framework.GameTestServer           <- Mojmap

PatchedMcBuilder's clean.jar                          Main$1  644 bytes
  final apn a;                                                        <- obfuscated
  invokevirtual apn.a:(Z)V                                            <- obfuscated
```

**Forge's binpatches are built against the DEOBFUSCATED jar. `PatchedMcBuilder` applies them to the obfuscated one.**
Its nine steps are: BUNDLER_EXTRACT, mergetool `--merge --ann API`, extract binpatches, binarypatcher, overlay,
access transformers, covariant self(). **There is no deobfuscation step, and no renaming step either** - an earlier
guess that `ForgeAutoRenamingTool --reverse` was a no-op on 26.2 was wrong; that tool does not appear in this file.

No SRG mappings are available anywhere in this tree or in the userdev jar (`forge-userdev.jar` holds only
`config.json`, `joined.lzma`, and `patches/*.java.patch`), so adding the missing step means obtaining mappings.
Mojang's own `client-1.21.1.txt` is already present under `namespace-probe/`.

### What is already correct, and can be used as-is

Naming shapes measured across the whole jars:

```
forge-probe-1211/patched-mc-forge-1.21.1.jar              9,478 classes   obfuscated short names: 0
nfrt-probe-1211/.../neoforge-21.1.249-merged.jar          9,768 classes   obfuscated short names: 0
forbric-kernel/.dev/minecraft/versions/1.21.1/1.21.1.jar  8,269 classes   obfuscated short names: 5,344
```

Both patched bases are **pure Mojmap**, which is exactly what `MergedBaseBuilder` expects. The vanilla client is not,
which is the one piece missing for the shortcut path below.

### Two ways forward

**A. Shortcut (unproven).** Deobfuscate the 1.21.1 vanilla with the Mojang mappings already in the tree, then feed
all three Mojmap jars to `MergedBaseBuilder`. Gets a launch attempt without touching `PatchedMcBuilder`. It is a
WORKAROUND, and it leaves the build pipeline still unable to produce a 1.21.1 base on its own.

**B. Correct fix (unproven).** Add the deobfuscation step to `PatchedMcBuilder` so the Forge side is built the way
Forge builds it. Requires mappings and touches the build path shared with 26.2, so it needs the 26.2 baseline
re-verified afterwards.

Note from stage 0: a `CONFLICTS: methods 1036` figure for 1.21.1 versus `1119` for 26.2 **was reported earlier and is
withdrawn**. Both runs used inputs that do not reproduce the shipped base, and the 1.21.1 run used the wrong tool
copy, so the comparison had no baseline. Do not reuse those numbers.

## The conflicts, measured comparably

Same tool (`forbric-kernel/src/tools`, including the collect-mode patch), same mode, both sides pure Mojmap. **The
line that matters is the second one, not the `CONFLICT-COLLECTED` count** - a mistake worth recording because it was
made three times:

```
1.21.1  [merge] classes: vanilla=2 forge-only-ns=1200 forge=97 neo=9077 MERGED=600 (superclass-rebased-to-forge=1)
1.21.1  [merge] CONFLICTS: methods=1029 fields=2 STRUCTURAL(superclass/field)=26 collision-methods-dropped=2

26.2    [merge] classes: vanilla=0 forge-only-ns=3 forge=185 neo=10155 MERGED=628 (superclass-rebased-to-forge=2)
26.2    [merge] CONFLICTS: methods=1117 fields=8 STRUCTURAL(superclass/field)=27 collision-methods-dropped=3
```

Read those fields correctly:

- `CONFLICT-COLLECTED #N` lines are only the cases that **threw** in default mode and were caught by collect mode.
  On 1.21.1 that is 4 lines. It is **not** the conflict count.
- `CONFLICTS: methods=...` is the real count. `vanilla=2` means "only 2 classes came from vanilla alone", not "only 2
  vanilla classes were seen" - most classes come wholesale from one of the two patched jars.
- `MERGED=600` is how many classes existed on **both** sides and therefore needed actual merging.

**On every conflict metric 1.21.1 is slightly better than 26.2**, not worse:

```
                   1.21.1   26.2
methods              1029    1117
fields                  2       8
STRUCTURAL             26      27
MERGED                600     628
```

This is consistent with the `1036 vs 1119` figure that an earlier revision of this document withdrew. **That
withdrawal was itself the error**: the number had been produced with the wrong tool copy and unverifiable inputs, so
re-measuring was right, but the conclusion drawn from that ("the figure was meaningless") was not - the figure was
essentially correct and it is now reproduced from a run whose inputs are two pure-Mojmap patched jars.

```

## Why conflict #1 cannot be fixed by relaxing a check

`Entity.getMaxHeightFluidType()` exists in both patched jars with identical arguments and different return types:

```
Forge      public net.minecraftforge.fluids.FluidType        getMaxHeightFluidType()
NeoForge   public net.neoforged.neoforge.fluids.FluidType    getMaxHeightFluidType()
```

Neither `FluidType` is an ancestor of the other - they are two unrelated classes with the same simple name.

The throw comes from one place, `MergedBaseBuilder.java:1024`, inside the `bm == null` branch. That branch already
recognises the situation (its comment says these are the same conceptual method, retyped by each compiler to its own
extension type, and that it should "reconcile to whichever ancestor we ACTUALLY chose") but **the reconciliation is
not implemented**: `boolean handled = false;` is never assigned `true`, so the only outcomes are the throw or a
straight splice.

`compatibleReturnContracts` (line 599) is **not** the bug. It accepts only one narrow shape: every `ARETURN` must be
preceded by a read of a field of the owner class, whose type is assignable to the return type - i.e. a cached-field
accessor. `getMaxHeightFluidType()` walks a map to find the highest entry, so it is correctly rejected.

Which means fixing this requires a **design decision**, not a code fix: on 1.21.1, which `FluidType` should the merged
`Entity` expose, or does it need a bridging class? That decides which ecosystem's mods work, and it is a question
about Forbric's intent rather than about the merge tool.

`ChunkGenerator` ("Incompatible initializer dependency") and `ItemBlockRenderTypes` ("retyped return") are separate
branches and have not been examined.

## 26.2 still cannot be reproduced here

Recorded because it keeps being assumed otherwise: running the active tool on 26.2 in **default** mode aborts on

# DANGER: `dev.py prepare` for 1.21.1 overwrites 26.2's state

`ArtifactBuilder.build()` writes `.dev/minecraft/.forbric-build/out/forge-runtime.jar` **first**, at
`ArtifactBuilder.java:101`, before the merge and before the `binarypatcher` step that currently fails. That filename
carries no version, so both lines share it. **A 1.21.1 `prepare` run therefore replaces the 26.2 Forge carrier on its
way to failing**, and the failure means nothing regenerates it.

Anyone touching this should either back that file up first, or make the path version-qualified before running prepare
for a second version. This is recorded here because it was found by a subagent reading `ArtifactBuilder`, not by
running into it - and earlier rounds of this port did run 1.21.1 prepares, so the 26.2 carrier may already have been
overwritten on this machine.

# The real size of the port: 151 runtime sources, 810 compile errors

An earlier revision of this document said the 26.2 audit found "about 15 lines to rewrite". **That estimate was wrong
by roughly fifty times**, and the reason is worth keeping: it was based on how few places name the version string.
Naming a version and depending on a version's API are different questions, and the kernel does the second one
constantly.

Measured by compiling the kernel's runtime source set against staged 1.21.1 artifacts:

```
810 errors across 151 runtime sources
```

Roughly a hundred corners of it, along three independent version axes:

| Axis | What is gone | Example |
|---|---|---|
| **Minecraft 26.x -> 1.21.1** | classes renamed between the versions | `net/minecraft/resources/Identifier` is gone; 1.21.1 has `ResourceLocation`. **101 uses.** Also `PackFormat`, `FuelValues`, `TooltipDisplay`, `EntitySpawnReason`, `SubmitNodeCollector`. |
| **Forge/NeoForge 26.x -> 1.21.1** | EventBus 7 API vs 6.2.33 | `eventbus.api.bus.EventBus<T>`, `BusGroup`, `listener.SubscribeEvent` do not exist; 1.21.1 ships `IEventBus`. Also `neoforgespi.transformation.*` and `fml.classloading.transformation.*`. |
| **fabric-api transfer 0.155 -> 0.116** | the API was renamed | `ItemVariant`/`FluidVariant`/`Storage` are 26.2 names; 1.21.1 has `ItemResource`/`FluidResource`/`TransactionContext`, plus `ResourceHandler`, `EnergyHandler`, `Operation`. |

This is **not** a staging hole, and that was checked in both directions: `ResourceLocation` and `FMLPaths` are present
in the staged jars, so the classpath resolves, and the missing symbols are genuinely absent from 1.21.1.

## What assembling the artifacts did teach

Nine of the eleven staged artifacts can be produced from what is on this machine. The two that cannot are the canary
mods, whose sources do not compile against 1.21.1 for the same reasons as the kernel.

The stock `assemble-*.sh` scripts **hardcode 26.2 auxiliary library versions**. 1.21.1's FML wants eventbus 6.2.33 and
forgespi 7.1.5 where 26.2 wants 7.0.1 and 8.0.0; mixing them assembles cleanly and fails later. Versions have to come
from each line's own userdev `config.json`, not from those scripts.

50 of 1.21.1's 54 Minecraft libraries are absent from `.dev/minecraft/libraries`, which holds 26.2's versions, so
`ready()` stays false until `stage_minecraft()` runs for 1.21.1.

## So what remains

Porting 151 runtime sources along three API axes. That is the whole of stage 4. Nothing about launching can be
measured until it is done, because no kernel jar exists to launch.

## The names are mutually exclusive, so there is no rename

Every symbol on this axis is present on exactly one line:

```
net.minecraft.resources.Identifier         26.2=PRESENT  1.21.1=absent
net.minecraft.resources.ResourceLocation   26.2=absent   1.21.1=PRESENT

`WeightedList`/`WeightedRandomList`, `AbstractBoat`/`Boat`, `TriState`, `Hud`, `ValueInput`. So a blanket

`Identifier` occurrences are **type positions** (declarations, generics, `.class` literals), which no wrapper or
helper can absorb, because every vanilla call takes and returns the real type.

## The mechanism: a declared rename table, applied at build time

`forbric-kernel/src/runtime/mc-line/1.21.1.tsv` holds `<26.2 name> TAB <1.21.1 name>`. The Gradle task
`normalizeRuntimeJava` copies `src/runtime/java` into `build/generated/mc-line/<line>/java`, applying the table
whole-token and longest-name-first, and the runtime source dir is pointed at that copy. This is the compile-time
twin of what `ForbricMappings` already does to bytecode at runtime.

**On 26.2 nothing happens.** The task, the `srcDir` swap and the dependency are all inside
`if (mcLine != '26.2')`, so a default build's source dir is still `src/runtime/java` and no extra task joins the
graph. The line is chosen by `-Pforbric.mcLine`, then `FORBRIC_MC_VERSION` (the variable `tools/dev.py` already
reads), then 26.2.

Two guards, both exercised rather than assumed:

- a rule that matches nothing **fails the build** (a stale entry would otherwise become a compile error on the
  other line, which reads as an engine difference);
- a line with no table **fails naming the file**, never silently building as 26.2.

The table is names only. Member-level counterparts that change the *shape* of an expression
(`Minecraft.gui.setScreen` -> `Minecraft.setScreen`, `WorldVersion.packVersion():PackFormat` ->
`getPackVersion():int`, `Gui.overlay()`) are written down in the table's tail as facts, not as rules.

## Axis 2: what was a rename, and what was not

The one thing on this axis that a name table can express is EventBus 7's per-event static bus. 6.2.33 has no
such field; on 1.21.1 every one of those events is posted on the single game bus, whose declaration was read
from the staged 1.21.1 `forge-runtime.jar`:

```
public static final net.minecraftforge.eventbus.api.IEventBus EVENT_BUS;   (net.minecraftforge.common.MinecraftForge)
```

26 rules `X.BUS` -> `net.minecraftforge.common.MinecraftForge.EVENT_BUS` are now in the table, one per event
class, and they account for **26 of the 26 errors removed** (164 -> 138, exactly one per rule).

The interesting part is the six sites that look identical and got no rule:

- `SpawnPlacementRegisterEvent.BUS` and `RegisterClientReloadListenersEvent.BUS` both implement
  `net.minecraftforge.fml.event.IModBusEvent` (javap). They fire on the **mod** bus, which has no name at all
  in 6.2.33 — it is reached through `FMLJavaModLoadingContext.get().getModEventBus()`, an expression. A rule
  would compile and silently deliver the event to nobody.

## What was remapped, and the modules that needed it - verified, not assumed

Measured over the three modules `extractTransferApis` pulls out of `fabric-api-0.116.17+1.21.1.jar`, counting

Minecraft classes and 244 member references** (the per-module columns overlap; the last row is the union) -
small enough to enumerate, which is why the failure was measurable at all rather than diffuse.

The remap is `remapTransferApis` in `forbric-kernel/build.gradle`, registered only inside the existing
`if (mcLine != mcLineDefault)` guard, so the 26.2 build graph does not gain a task (verified: `--dry-run` of

against the latter on that line and against the former on 26.2 - one variable, chosen by `mcLine`.

Three things it does beyond a `SimpleRemapper`:

- **Hierarchy walking.** A call site's owner is the static receiver type, not the declaring class.
  `class_1657.method_23317` is declared on `class_1297`; **38 of the 244 references resolve only through a
  supertype.** It also matters for declarations: `AbstractFurnaceBlockEntityMixin` extends a Minecraft class, so
  its own overriding declarations must be renamed with their target.
- **Entry names, not only bytes.** Output entry names come from the same name function, so an inner class moves
  with its outer (`class_2350$class_2351` -> `Direction$Axis` in both places). **No class in these three modules
  is Minecraft-named**, so the real run renames zero entries - the path is proved by a `--selftest` mode that
  builds a jar holding `net/minecraft/class_1799` and its inner class, remaps it, and asserts the entry names,
  the field descriptor and the method names moved (`SELFTEST PASS`, 2 of 2 entries renamed).
- **A verification pass against a real Mojmap jar.** Every class, descriptor, signature, annotation type, LDC
  type and member reference in the OUTPUT is resolved against the staged merged base, walking supertypes, and
  the task fails if one does not. Result: **742 references checked (275 class, 145 field, 322 method), 0
  unresolvable**; 1 member unchecked because its owner chain leaves the base (`Container.toString()`, inherited
  from `java/lang/Object`), and 87 non-Minecraft owners (other fabric modules, guava) which the remap does not
  touch. The remap itself is deterministic: two runs over the same inputs produce byte-identical jars, because
  the entry timestamps are fixed.

The table is `src/runtime/mc-line/1.21.1-fabric-ns.tsv` - a declared, reviewable file, like the rename table,
not something inferred inside a task. It covers the **closure** the modules need: 175 classes and 10,352
members, supertypes included. A name it lacks is reported by the task and fails the build.

## The join behind that table is not the one `emit-table.ps1` does, and the difference is a defect

`tools/namespace/emit-table.ps1` keys members by `(obfOwner, kind, obfName)`. That key is **lossy**: one
obfuscated class reuses a short obf name for many methods that differ only in descriptor - `bsr.a` alone covers
81 - so **8,744 of 70,511 obf keys in `client-1.21.1.txt` carry more than one Mojmap name**, and whichever the
join saw last wins. `tools/namespace/join-keyed.py` adds the descriptor *and* the obf member name to the key:

```
78,922 of 78,922 members joined (100.0%), 0 ambiguous       join-keyed.py
77,152 of 78,922 members joined ( 97.7%)                    the shipped pipeline
```

Two further traps had to be fixed to get there, both silent: **client.txt's obf column is a DOTTED class name**
for the 34 classes Minecraft does not obfuscate (`net.minecraft.server.MinecraftServer`), while tiny writes the
same class slashed - 454 members; and the `10:10:` line-range prefix on client.txt method lines must be stripped
before anything else, or the return type parses as `911:911:boolean` and 40,686 of 41,243 methods join with
nothing.

**This is not only a build-time matter.** `KernelMappingResolver` reads exactly the `C/M/F` format
`emit-table.ps1` writes, so the shipped runtime table carries the same defect. Measured against the merged base:

| property | shipped table | descriptor-keyed table |
|---|---|---|
| member records | 77,152 | 78,922 |
| records where the two tables disagree on the name | 27,074 | - |
| of those, the other table's name is the one present at that owner+signature | 11 | 22,410 |
| two intermediary members mapped onto ONE Mojmap member | **4,025 targets / 8,241 records** | **0** |

A correct join is one-to-one onto Mojmap's member set, so 4,025 colliding targets are impossible rather than
merely unlikely. The corrected full table is one command
(`python tools/namespace/join-keyed.py <out> --full`); it is **not** wired in here, because swapping the runtime
mapping table is a behaviour change on this line and belongs to its own change.

# The runtime mapping table, replaced: 22,861 verified-wrong records to 0

The previous section ended by naming a defect it had measured and deliberately did not fix: `emit-table.ps1` keys
members by `(obfOwner, kind, obfName)`, which is lossy, so the table that `KernelMappingResolver` reads at runtime
carried that defect too, and swapping it was a behaviour change that belonged to its own change. This is that
change, and it does not rest on the join's own counts. It rests on the two questions a runtime table has to answer:
**does the resolver hand back exactly what the file says**, and **does that name exist at that owner and signature
in the game that runs**.

## Three ways this could have failed silently, and what each is measured by

1. **The join.** `tools/namespace/join-keyed.py --full` emits 87,176 records (8,254 C, 41,243 M, 37,679 F) from
   78,922 of 78,922 members joined, 0 ambiguous. (`--full` is now explicitly the runtime mode; the closure mode
   that feeds `NamespaceRemapper` is byte-identical to the committed `1.21.1-fabric-ns.tsv`, md5 `676dce98…`,
   so the compile-time remap is untouched.)
2. **The resolver's parsing of it.** A record the resolver cannot use does not throw: member records with fewer
   than four fields were dropped by an `if (f.length >= 4)` guard, and a table keyed differently from the lookup
   just misses. `net.forbric.kernel.fabric.MappingTableAudit` loads the table through the resolver — system
   property, static table, the real code path — and replays **every** record.
3. **The names being true of the game.** `tools/namespace/verify-runtime-table.py` resolves each record's
   descriptor from Fabric's own tiny mapping (neither side invents one), converts it from obf to Mojmap, and asks
   the jars whether `(name, descriptor)` exists on that owner.

## The format WAS different, and that is the finding

The table was swapped and the resolver was left alone first, on purpose, to see what it would say. It said:

```
                            shipped table                       descriptor-keyed table
mapClassName(slashed in)    net.minecraft.client.Minecraft      net/minecraft/client/Minecraft
unmapClassName(dotted in)   net/minecraft/class_310             net.minecraft.client.Minecraft   <- the input
mapMethodName(class_310)    lambda$buildInitialScreens$8        run
```

Three separate silent failures on one screen:

- **The keyed table's official class names are INTERNAL (slashed)**, because `join-keyed.py` also writes the table
  `NamespaceRemapper` feeds to ASM, where slashes are the form. fabric-loader's `MappingResolverImpl` answers
  **binary** names and rejects a `/` in its input, so a naive swap would have given every mod a name it cannot
  `Class.forName` — silently, with no error anywhere.
- **The reverse lookup answered nothing at all** from the keyed table, because the reverse map was keyed on the
  slashed spelling while a caller passes the dotted one.
- **`method_1514` mapped to `lambda$buildInitialScreens$8`** from the shipped table — the lossy join, visible in
  one lookup — and to `run` from the keyed table.

So the separator is no longer load-bearing in either direction. `KernelMappingResolver` reduces table keys and
query class names to the internal form and answers class names in binary form, which is what fabric-loader's
implementation does; a dotted query, which is the form that implementation documents, used to miss on **both**
tables and now hits. Measured after the change: replays of the two tables agree on **8,220 of 8,220** shared class
records — 0 differences — so the swap changes member names and nothing about class names. A three-field member
record now fails the load instead of being skipped.

# Stage 1.1: the transaction question, decided before any code

The previous section ended the axis-3 story with one sentence that is a decision, not a measurement:

> The blocker that outlives the types is the transaction. [...] a port must supply snapshot/rollback
> itself. That is code, not a name, which is why no rule was written and why the count on this axis did not
> move.

This section answers that question **before** any code is written, in the order the option space deserves,
and it is written down here first so that the code that follows can be judged against it.

## What the 26.2 bridge actually relies on

Reading `PairedTransactions` and `ForgeSnapshotAdapters` rather than the type list, the dependency is narrower
than "NeoForge transactions":

1. **The journal belongs to the provider, not to the bridge.** `ItemStackHandler` on 26.2 registers its own
   `SnapshotJournal` with the `TransactionContext` it is handed, and reverts itself when that context aborts.
   The bridge never snapshots a native store. `ForgeSnapshotAdapters` exists only for the *legacy Forge* store,
   which has no transaction of its own, and it journals that one on the bridge's side.
2. **The bridge pairs two engines.** `PairedTransactions` opens a NeoForge transaction that is a peer of the
   Fabric transaction the consumer holds, so that closing one closes the other at the same nesting boundary
   (`beforeClose`/`afterClose`, `TransactionTransactionHooks`). No value is ever copied across; the two engines
   just have to agree on when to commit.
3. **Therefore "half-succeeded cross-API insert" means**: a Fabric consumer's transaction did one real write
   into a NeoForge store and then aborted. The NeoForge store's own journal is what takes that write back.

So the port's problem is not "reimplement a transaction engine". It is: **on 1.21.1 the write into a
handler-API store is not journalled by anyone, because there is no context to hand it.**

## The four ways out, and which one is right

**A. One source tree that speaks handlers on both lines.** 26.2 still ships the legacy handler API
(`items.IItemHandler`, `ItemStackHandler`, `ItemHandlerHelper`, `fluids.capability.IFluidHandler`,
`energy.IEnergyStorage` -- javap in `neoforge-runtime.jar`), so a bridge written against handlers would
compile for 26.2 and 1.21.1 both, and the transfer package would not need a second edition at all.

**Rejected, and the reason is the question the stage asked me to answer.** On 26.2 the handler API is not the
same capability as the new API: `Capabilities.Item.BLOCK` is a `BlockCapability<ResourceHandler<ItemResource>,
Direction>` while `Capabilities.ItemHandler.BLOCK` is one over `IItemHandler` (javap both). A 26.2 mod that
registers its storage with the **new** capability would become invisible to this bridge, and therefore to every
Fabric consumer -- the bridge would keep working for old mods and silently stop covering new ones. The
direction that would keep both visible does not exist: 26.2 ships `items.ItemResourceHandlerAdapter`, which
adapts a *handler* **into** the new API. There is no adapter from a `ResourceHandler` back to `IItemHandler` to
pair it with. And the cost is not only conceptual: the transfer suite (`src/transferTest`) pins the
`ResourceHandler` shapes, the journal depths and the notification timing, so the single-tree route would have
to change the behaviour of the line that currently works, in a stage whose hard constraint is that it must not.

**B. Give up rollback on 1.21.1 and record the behaviour difference.** There are two versions of this and both
are worse than they look:

- *Expose nothing that cannot be rolled back.* That is what the 26.2 code already does for unauditable
  providers (`FORGE_HANDLER_NOT_ROLLBACK_SAFE`), and on 1.21.1 the same policy would refuse **every** store,
  because no handler has a journal. The bridge would be a switch that installs and then answers nothing --
  dead code with extra steps.
- *Expose it anyway, and document that abort does not undo.* This is not a smaller contract, it is a broken
  one: a Fabric consumer's `simulate` (which is *defined* as an operation followed by an abort) would really
  mutate the neighbour's inventory, and `ContainerStorage`-style double moves would duplicate or destroy
  items. Documenting a corruption path is not porting it, and the error count would move by an act of
  documentation.

**C. Implement the snapshot ourselves, driven by the transaction that survives.** **This is the answer.**

**D. Delete the transfer component from the 1.21.1 line** (don't overlay the package; the errors go away
because the code does). Rejected without much agonising: it is the only option that would reduce the number by
removing the capability the number is about, and the bridge is the reason this kernel exists. It would also
make `1.3`'s "axis 3 drops" true and worthless.

## Why C is available: the transaction did not disappear, one of its two engines did

Fabric's transfer API is a *mod*, identical on both lines, and 1.21.1's copy has the whole transaction
machinery. Measured by javap against the 1.21.1 measurement class path:

```
net.fabricmc.fabric.api.transfer.v1.transaction.TransactionContext
  openNested() / nestingDepth() / getOpenTransaction(int)
  addCloseCallback(TransactionContext$CloseCallback)
  addOuterCloseCallback(TransactionContext$OuterCloseCallback)

net.fabricmc.fabric.api.transfer.v1.transaction.base.SnapshotParticipant<T>
  abstract T createSnapshot(); abstract void readSnapshot(T); void releaseSnapshot(T);
  void onFinalCommit(); void updateSnapshots(TransactionContext);
  void onClose(TransactionContext, TransactionContext$Result);
  void afterOuterClose(TransactionContext$Result)
```

`SnapshotParticipant` **is** NeoForge's `SnapshotJournal`, under Fabric's name, and it is the protocol Fabric
documents for exactly our case: a storage whose writes must be reversed when the transaction that made them
aborts, at the nesting depth at which they were made. So the port is not "write a transaction engine"; it is
"move the snapshot to the side that still has one".

The mapping, operation by operation:

| 26.2 | 1.21.1 |
|---|---|
| bridge hands the consumer's `TransactionContext` to a native store, whose own journal registers with it | bridge captures a snapshot of the handler store **before** mutating and registers it with the consumer's Fabric `TransactionContext` |
| abort at depth *n* -> the store's journal reverts to its depth-*n* snapshot | abort at depth *n* -> `SnapshotParticipant.onClose` reverts to the depth-*n* snapshot |
| commit -> `onRootCommit` runs the deferred `setChanged()` callbacks once | commit -> `afterOuterClose` runs them once |
| unauditable Forge store -> no view, `FORGE_HANDLER_NOT_ROLLBACK_SAFE` | identical policy, identical issue code |
| a Fabric consumer's `simulate` = open nested, insert, abort | identical (Fabric's own transaction, unchanged) |
| a Forge/Neo consumer's `simulate` (no transaction of its own) = open a scope under the current one, do it, abort or commit | identical, minus the Neo half of the pairing |

Three consequences that are properties of the design, not accidents:

- **`simulate` is never trusted.** On 26.2 a `ResourceHandler` has no simulate flag, so a write is always real
  and always journalled; on 1.21.1 a handler *does* have the flag, and the bridge still does not trust it:
  every mutating call goes through a snapshot. That is strictly stronger than `insertItem(..., true)`.
- **The bridge is now the only transaction there is** for a NeoForge-native store on 1.21.1, because on that
  line a NeoForge store *is* a handler. There is no native journal to defer to, and the code says so instead of
  implying otherwise.
- **What cannot be certified the same way.** 26.2's reversibility certificate is a set of post-transform
  **bytecode fingerprints** (`ForgeTransferShapeAudit.AUDITED`, e.g.
  `net.minecraftforge.items.ItemStackHandler -> be15e7bb...`). Those hashes are of 26.2 bytes and cannot match
  1.21.1's. The 1.21.1 edition therefore certifies by **shape** -- exact class (no subclass can override a
  transfer method), the audited private field layout, and no foreign override of the helpers -- and this
  document says plainly that it is weaker in exactly one respect: a third party that *transforms* the standard
  class itself would not be noticed, where the fingerprint would notice. Producing a 1.21.1 fingerprint set is
  a separate job (it needs a 1.21.1 emit pass) and is **not** done here.

## What genuinely cannot be ported, said now rather than discovered later

The **Forge-consumer direction has no seam on 1.21.1.** `ForgeTransferCapabilityFallback` injects into
`BlockEntity.getCapability(Capability, Direction)`, and that method does not exist on the 1.21.1 merged base:

```
$ javap -cp <1.21.1 measurement class path> net.minecraft.world.level.block.entity.BlockEntity
  ... no getCapability(Capability, Direction) anywhere in the class ...
  implements ... net.minecraftforge.common.extensions.IForgeBlockEntity
$ javap ... net.minecraft.world.level.block.entity.BaseContainerBlockEntity
  public <T> LazyOptional<T> getCapability(Capability<T>, Direction);     <- only here
```

So on 1.21.1 Forge mods' `getCapability` calls cannot be extended by that transformer, and the bridge reports
`FORGE_QUERY_HOOK_MISSING` exactly as 26.2 does when a hook is absent. Two things this does **not** break,
which is why the rest of the axis is still worth porting:

- **Reading** a Forge owner's store needs no hook: it is a direct
  `ICapabilityProvider.getCapability(capability, face)` call on the block entity, which 1.21.1 has.
- The **NeoForge-consumer** direction has its seam: `BlockCapability.getCapability(Level, BlockPos,
  BlockState, BlockEntity, C)` exists on 1.21.1 (javap), which is what `TransferCapabilityFallback` targets.
- The **Fabric-consumer** direction is public API (`BlockApiLookup.registerFallback`), unchanged.

One more API fact that follows from the same javap: `Level.getCapability` does not exist on 1.21.1 either, so
every native query in the 1.21.1 edition goes through `Capabilities.ItemHandler.BLOCK.getCapability(...)`
rather than `level.getCapability(...)`.

## Where the decision is enforced in the code

The 1.21.1 edition of the transfer package is an **overlay**: `src/runtime/mc-line/1.21.1/java/` replaces the
files that name the absent package, through the same `-Pforbric.mcLine` knob that already normalises the
sources -- no second version switch. Files that are already line-neutral (`TransferPrecedence`,
`TransferIssues`, `EnergyUnits`, `ForgeCapabilityWatch`, `KernelFabricHopperStorage`, `package-info`) stay
shared, so the two lines cannot drift apart on the decisions they agree about. The overlay list is 13 files,
exactly the 13 that carry axis-3 errors, and the build fails if an overlay file does not replace a real source
file (so the list cannot rot into a pile of new files nobody deletes).

The internal currency of the 1.21.1 edition is the **NeoForge handler** (`items.IItemHandler`,
`fluids.capability.IFluidHandler`, `energy.IEnergyStorage`), for the same reason the 26.2 edition's currency is
`ResourceHandler`: it is the richest handler API on its own line. Cross-ecosystem paths then compose through
it -- Fabric <-> NeoForge in `NativeTransferAdapters`, Forge <-> NeoForge in `ForgeLegacyFacades` -- instead of
growing an adapter for every pair.

## What stage 1.3 measures, and what it will not prove

`1.3` is a count: axis 3 must fall, cascades must not rise. It is worth writing down in advance that **a lower
count is not evidence that the semantics above are right**. The journal is exercised by the 26.2 transfer tests
only; the 1.21.1 edition of it has never been loaded, and nothing in this stage can change that.

- **No handler is ever asked to simulate.** `insertItem(slot, stack, simulate)` exists on this line; the bridge does

- **The Forge-consumer direction is dormant and says so.** `install()` reports `FORGE_QUERY_HOOK_MISSING` because

## The method that found the two renames, and why the two earlier ones could not

The previous rounds swept by **class simple name** (`rename-sweep.py`, word overlap over all 39 jars on the 1.21.1
measurement class path). That sweep is exhaustive for a class that moved, and it is blind to a rename whose owner did

## The mechanism discovery: an overlay steals the rules that only match inside it

This is the one thing in this round that changes how the mechanism has to be used, and it was found by the guard
rather than by reading the code. `normalizeRuntimeJava` writes overlay files **verbatim, with no rule applied**, and
its "a rule that matched nothing fails the build" guard counts matches over the **non-overlaid** tree. So a table row
whose only call site lives in a file that later becomes an overlay starts matching nothing and **fails the build**:

```
> E:\...\src\runtime\mc-line\1.21.1.tsv: 1 rule(s) matched nothing in src/runtime/java:
  [net.minecraftforge.event.entity.living.LivingExperienceDropEvent.BUS].
```

An earlier section of this document says that guard "still runs against the pre-overlay sources, so a table row whose
only match lived in an overlaid file is still counted". **That sentence is wrong** and is corrected here: the guard
skips overlaid files entirely, both for the substitution and for the count. Exactly one rule was affected — the
`LivingExperienceDropEvent.BUS` row, whose single site is `KernelGameServerEvents`, which this round overlays for the
`onExplosionDetonate` arity. The row is commented out in place with that reason written beside it, rather than deleted
silently. The trade is 1 error either way and the overlay is worth more.

## Group A — `BusGroup` has a counterpart, and it is not a `BusGroup`

`javap` on both carriers (`run/forge-runtime/forge-runtime.jar` for 26.2,
`.dev/staged-1211/run/forge-runtime/forge-runtime.jar` for 1.21.1) says the two lines ship **different eventbus
generations**, and the API the kernel calls exists on exactly one side each:

| | 26.2 (EventBus 7) | 1.21.1 (EventBus 6) |
|---|---|---|
| `net.minecraftforge.eventbus.api.bus.BusGroup` | **present**: `DEFAULT`, `create(String)`, `create(String, Class)`, `name()`, `startup()`, `shutdown()`, `dispose()`, `trim()`, `register(Lookup, Class/Object)`, `unregister(Collection)` | **absent** — the whole `api.bus` package is four classes (`BusGroup`, `CancellableEventBus`, `EventBus`, `package-info`) and `api.bus.BusGroup` does not resolve |
| `net.minecraftforge.eventbus.api.BusBuilder` | **absent** on the 26.2 carrier | **present**, and it is an *expression*: `builder()` → `markerType(Class)` → `build(): IEventBus`, plus `setTrackPhases`, `setExceptionHandler`, `useModLauncher`, `startShutdown`, `checkTypesOnDispatch` |

| `RegisterEvent.getBus(...)` | `public static EventBus<RegisterEvent> getBus(BusGroup)` | **no such member**, and `RegisterEvent extends net.minecraftforge.eventbus.api.Event` instead of a child of `net.minecraftforge.eventbus.internal.Event` |

Three consequences, and they are why this group is three overlay files rather than three table rows:

1. **The type changes, and so does the field that must receive it.** The kernel writes that field *by name*
   through `UnsafeHacks`, so javac checks the type and nothing checks the name:
   `uset(FMLModContainer.class, "eventBusGroup", …)` is a `NoSuchFieldException` at runtime on 1.21.1 that the
   compiler cannot see. `"eventBusGroup"` → `"eventBus"` is part of the port, not a tidy-up.
2. **The creation form changes.** `BusGroup.create("modBusFor" + modId, IModBusEvent.class)` is a static factory
   that takes a NAME; 1.21.1's is `BusBuilder.builder()…build()`, and `BusBuilder` has no name parameter.
3. **The post form changes.** 26.2 routes each event class to its own bus through a per-event static
   `X.getBus(group)`; 1.21.1 posts to its single bus directly. Substituting the type and leaving `.getBus(group)`
   does not compile — and the group is eight *reported* errors, not eight broken lines: `javac` suppresses the seven
   `getBus` call sites because the argument's type is already erroneous (measured — the `before` transcript has no
   error on any of those seven lines, only on the import, the signature and the cast), so `KernelForgeSetup` costs
   3 reported errors for 10 changed lines. The compile count understates this group's work by seven.

What 1.21.1's own loader does with that builder was read out of its bytecode rather than guessed
(`javap -c net.minecraftforge.fml.javafmlmod.FMLModContainer`, the constructor): `BusBuilder.builder()` →
`setExceptionHandler(<invokedynamic>)` → `setTrackPhases(false)` → `markerType(IModBusEvent.class)` →
`useModLauncher()` → `build()` → `putfield eventBus:IEventBus`, with no `start()` anywhere in the constructor.

### The port

Three files are overlays — `KernelForgeContainers`, `KernelForgeSetup`, `KernelForgeRegistries` — because every
difference above is an expression or a type, never a spelling. **No rename-table row was added**, so the "an
overlay steals the rules that only match inside it" trap could not fire; that was checked rather than assumed:
`build/x11/overlay-rules.py` reproduces `normalizeRuntimeJava`'s guard (whole-token, longest-rule-first, overlay
files skipped) over the 47 existing rules and reported **0 orphaned by the 22-file overlay set**, before the files
were written and again after.

- `KernelForgeContainers` — `IEventBus` instead of `BusGroup`; the bus is built by a private `modBus()` that
  carries the disassembly above, with **two builder calls deliberately not reproduced**, each named in its javadoc:
  `setExceptionHandler` (the carrier passes its own `onEventFailed`, which logs through `FMLModContainer`'s
  markers; the bus's own default handler — `EventBus` implements `IEventExceptionHandler` — is what a builder that
  sets none gets) and `useModLauncher()` (that flag selects `ModLauncherFactory`, whose `createWrapper` **enqueues**
  the generated listener class for modlauncher's transformer instead of defining it, and
  `ModLauncherFactory.processWrapperClass` is the only drain; this kernel's loader is not that pipeline, so the
  queue would never drain and no listener would materialise, while the default `ClassLoaderFactory` defines the
  wrapper itself). The field write becomes `"eventBus"`; `startup()` becomes `((IEventBus) bus).start()`.
- `KernelForgeSetup` — the seven `X.getBus(group).post(new X(container, stage))` become `bus.post(new X(…))`. That
  is legal on this line for a checked reason: on 1.21.1 every lifecycle event reaches `Event` through
  `ModLifecycleEvent extends net.minecraftforge.eventbus.api.Event`, which is the base class `IEventBus.post`
  requires — and it is a *difference*, not a detail: on 26.2 `ModLifecycleEvent` does not extend `Event` at all
  (`javap` both).
- `KernelForgeRegistries` — the single `RegisterEvent.getBus((BusGroup) busGroup).post(event)` becomes
  `((IEventBus) busGroup).post(event)`. Nothing stands in for the missing per-event lookup, because on this line
  there is nothing to look up.

**Two facts the port states rather than translates.** First, `startup()` on 26.2 is not the "no event dispatches
before this" gate the kernel's javadoc claimed: `BusGroupImpl.startup` iterates the group's buses into
`AbstractEventBusImpl.startup`, whose body is `shutdownFlag.compareAndSet(true, false)` plus an invoker re-arm, and
1.21.1's `IEventBus.start()` is the same idea one generation smaller (`shutdown = false`, and `post` answers false
while it is set). A freshly created bus of either generation dispatches as soon as it exists. The claim was wrong
on 26.2 too, so it was corrected instead of translated. Second, a field this kernel has never had to write on 26.2
exists on 1.21.1: `ModContainer.configHandler` is `protected Optional<Consumer<IConfigEvent>>` there, `ModContainer`'s
own (skipped) constructor writes `Optional.empty()` into it, and `dispatchConfigEvent` reads it with `orElse(null)`
and dereferences the result (`javap -c`), so a null field is an NPE the moment anything dispatches a config event.
The overlay restores `Optional.empty()` — the value the skipped constructor would have left, so a reconstruction and
not a handler — beside the four fields the shared file already restores for the same reason.

**One thing is lost and is written into the code:** 26.2 names each group (`"modBusFor" + modId`) and the name is
what its diagnostics print; `BusBuilder` takes no name, so on 1.21.1 a mod bus is identifiable only by the kernel's
own log lines.

### The measurement that settles it: the merged base's own manifest

Both merged bases ship `META-INF/forbric/required-ancestor-compositions.tsv`, and `ForbricClassLoader.define`
runs every definition through `RequiredAncestorCompositions.verify`, which throws `LinkageError` when no registered
`AncestorComposition` proves the class's final bytes. The two files, read out of the jars:

```
26.2    Entity       AttachmentHolder   CapabilityProvider$Entities
        Level        AttachmentHolder   CapabilityProvider$Levels
        BlockEntity  AttachmentHolder   CapabilityProvider$BlockEntities

1.21.1  Entity       AttachmentHolder   CapabilityProvider
        EnderDragonPart  PartEntity     PartEntity          (neoforged -> minecraftforge, a separate row)
        Level        AttachmentHolder   CapabilityProvider
        BlockEntity  AttachmentHolder   CapabilityProvider
```

**That is the capability-model change, in one table.** 26.2 removed a *different provider class per root*, and each
of those classes is exactly the thing that carries a per-root `AttachCapabilitiesEvent` subclass. 1.21.1 removed
*one class* for all three roots and parameterises it with a `Class` literal. The kernel's
`KernelForgeCapabilities.Entities/$BlockEntities/$Levels` are not three spellings of one thing on this line — there
is nothing per-root for them to return, and the only thing that distinguishes the three is the argument.

And the install half cannot be ported by editing the runtime class, because its preconditions are 26.2 classes.
`ForgeCapabilityProtocol.protocol(removed, …)` requires, for the removed provider: `super == CapabilityProvider`,
**no fields**, and a constructor whose token stream is `[v25:0, o3, m183:CapabilityProvider.<init>(Z)V, o177]`; and
for `AsField`, a constructor `<init>(Lnet/minecraftforge/common/capabilities/ICapabilityProviderImpl;Z)V`. On
1.21.1 the removed provider for all three roots **is** `CapabilityProvider`, whose superclass is `java/lang/Object`
and which has eight fields, and `AsField`'s constructor is `(Class, ICapabilityProviderImpl)` — so `protocol()`
returns false on its first `&&`, `certificate()` returns null, `proves()` can never be true, and the loader throws
`LinkageError` on `Entity`, `Level` and `BlockEntity`. That is a **launch blocker on 1.21.1 that no compile-axis
work removes**, and it is the same subsystem as these 14 errors.

### The four routes, and why the first three are worse

- **PORT THE RUNTIME HALF ONLY (overlay the file: Class-keyed `AsField`, no overrides, `injectCapabilities(ModList.get())`,
  `CompoundTag` save/load).** This is what the compile count wants, and it is the route that was refused. It would
  remove **29** errors, not 14: `KernelForgeCapabilities.java` also carries 6 axis-1 `ValueInput`/`ValueOutput`
  symbols and 9 cascades (six "method does not override or implement a method from a supertype", one
  `getAllScanData` static-context error — the same instance-API `ModList` change stage 2 made — and the two
  `ValueInput`/`ValueOutput` import failures folded in), and an overlaid file has to compile whole. What it would
  produce is a correct class that **nothing constructs**, because the one part of the subsystem that installs it
  still cannot run on this line. The count would fall while the blocker stayed exactly where it is. That is the
  shape stage 1.1 refused twice: "a switch that installs and answers nothing" is not a smaller contract, it is a
  broken one — and here it is worse than a switch, because a class that compiles reads as ported.
- **KEEP THE THREE SUBCLASSES AND GIVE THEM `Class` ARGUMENTS WITHOUT TOUCHING THE PROTOCOL.** Same objection one
  level down: the three classes would exist to pass `Entity.class`/`BlockEntity.class`/`Level.class` and nothing
  else, while the protocol that is supposed to fingerprint them can never see them.
- **REWRITE THE COMPOSITION TO THE 1.21.1 SHAPE HERE.** This is the only route that would actually work, and it is
  not this group: it needs a second certificate (one-provider shape, `AsField(Class,B)` tokens,
  `$Composed.<init>(Class, Object)`), new delegate descriptors for `saveAdditional(CompoundTag,
  HolderLookup.Provider)` / `saveWithoutId(CompoundTag)` instead of the `ValueOutput` seams, and a new set of
  injection anchors — all boot-side transformer work, with its own tests (`ForgeCapabilityProtocolTest`,
  `ForgeCapabilityCompositionTransformerTest`), and none of it in the 14.
- **DO NOTHING AND SAY WHY (chosen).** The 14 errors stay, the total stays where Group A left it, and the next
  stage gets a decision with the evidence attached instead of 27 errors' worth of dead code.

### What a 1.21.1 edition needs, so the next stage does not have to re-measure it

1. **A protocol certificate for the one-provider shape.** `removed` is `net/minecraftforge/common/capabilities/CapabilityProvider`
   for all three roots (from the manifest), with `AsField(Class<B>, B)` — so the fingerprint must be taken from
   `CapabilityProvider`'s own field/constructor layout plus that constructor, not from a subclass that has none.
2. **Three accessors that differ only in a `Class` literal**, and `Inert` expressed as NEVER INITIALISING rather
   than as an override answering false: 1.21.1's `getCapability` does not auto-gather, so an un-initialised
   provider is empty forever, which is the same end state 26.2 reaches by marking the provider initialised with a
   null dispatcher.
3. **A save/load seam in `CompoundTag`**, because this line's roots save through
   `saveAdditional(CompoundTag, HolderLookup.Provider)` and `saveWithoutId(CompoundTag)` and have no
   `ValueInput`/`ValueOutput` at all (`serializeCaps(ValueOutput)` does not exist on this carrier; only the
   `HolderLookup.Provider` overload does).
4. **`injectCapabilities(ModList.get())`** — an instance API on this line, the same change stage 2 made in
   `KernelForgeDeclarationReaders`.

# Stage 4: the 1.21.1 certificate — the removed provider IS the carrier, so the proof keys on `baseClass`

This is the stage the previous round handed over. Its refusals are the premise: the runtime half of the capability
subsystem compiles on 1.21.1 but nothing installs it, and `ForgeCapabilityProtocol.protocol()` returns false on this
line for a reason that is in the bytecode. **The decision is written here before the code**, and the code, the counts
and the verification are appended below the decision.

## Decision, in one line

`ForgeCapabilityProtocol` gets a **second certificate shape**, selected by what the merged base's own manifest calls
the removed superclass — not by a property, not by a version string. When the removed class *is*
`net/minecraftforge/common/capabilities/CapabilityProvider`, the certificate must prove that the **Class argument** is
what selects the `AttachCapabilitiesEvent` subtype, because on this line that argument is the *only* place the
per-root distinction still exists.

## Why `protocol()`'s preconditions cannot be met on 1.21.1 — five checks, each a bytecode fact

The manifest rows are the same for all three roots on 1.21.1 (`sourceSuperclass` = `CapabilityProvider`), where 26.2
names a different `$`-nested provider per root. `protocol()` was written against the 26.2 rows, so every one of its
carrier preconditions asks about a class that on 1.21.1 is something else:

| `protocol()` asks | 26.2 (`removed` = `CapabilityProvider$Entities`) | 1.21.1 (`removed` = `CapabilityProvider`) |
|---|---|---|
| `BASE.equals(nativeProvider.superName)` | true — the nested class extends `CapabilityProvider` | **false** — `super = java/lang/Object` |
| `nativeProvider.fields.isEmpty()` | true — the nested class adds no state | **false** — 8 instance fields **plus** `SUPPORTS_LAZY_CAPABILITIES` (`baseClass:Class`, `capabilities`, `valid`, `isLazy`, `lazyParentSupplier`, `lazyData`, `registryAccess`, `initialized`) |
| `AsField.<init>(L…ICapabilityProviderImpl;Z)V` | true | **false** — this line has `<init>(Ljava/lang/Class;L…ICapabilityProviderImpl;)V` and the three-argument `(Class, B, Z)`; there is no `(B, Z)` constructor |
| `kind = removed.substring(lastIndexOf('$')+1)` | `"Entities"` → `KernelForgeCapabilities$Entities` | **no `$`** → the whole internal name → `KernelForgeCapabilities$net/minecraftforge/…` → `null` |
| the two abstract hooks | `fireAttachCapabilitiesEvent(B)` and `shouldFireAttachCapabilitiesEvent()` are `protected abstract`, which is exactly what `KernelForgeCapabilities$Entities/$BlockEntities/$Levels` implement | **absent**. `CapabilityProvider` declares no abstract method at all (`javap -p`: `abstractMethods=[]`), and `gatherCapabilities()` is `protected final` on both lines |

So the 26.2 subclass model has **no shape to occupy** here: there is no abstract method to supply and no non-final
hook to override. That is not a defect to be worked around; it is the line saying where its per-root key lives.

## The measurement that turns that into a design, not a compromise

`doGatherCapabilities` on 1.21.1, disassembled:

```
aload_0
aload_0 ; getfield baseClass:Ljava/lang/Class                   <- the Class ARGUMENT
aload_0 ; invokevirtual getProvider()L…ICapabilityProviderImpl; <- AsField.getProvider() returns `owner`
aload_1                                                         <- the optional parent
invokestatic ForgeEventFactory.gatherCapabilities(Class, ICapabilityProvider, ICapabilityProvider)
putfield capabilities ; initialized = true
```

and `ForgeEventFactory.gatherCapabilities(Class<? extends T>, T, ICapabilityProvider)` builds
`new AttachCapabilitiesEvent<>(baseClass, provider)` and posts it on the **one generic bus**. On 26.2 the same job was
done by `$Entities.fireAttachCapabilitiesEvent` naming `AttachCapabilitiesEvent.Entities`. **The per-root key moved
from the class to the argument.** That is why one provider class for three roots is correct on this line and a loss
on the other — and it is why the certificate's obligation changes from *"the removed class is the per-root provider"*
to *"the removed class is the state carrier, and the Class the delegate supplies is what the carrier keys the event
on"*.

A second, load-bearing corollary, also measured rather than assumed: `AsField(Class, B)` delegates to
`CapabilityProvider(Class)` → `(Class, false)`, and `isLazy = SUPPORTS_LAZY_CAPABILITIES && eager` — a tautological
`false` on that path whatever the static's value (it is `true`, from `<clinit>`: `iconst_1; putstatic; return`). With
`isLazy == false`, `getCapability` reads `getCapabilities()`, which cannot gather, and `capabilities` is null until
something calls `initInternal()`. So **an un-initialised provider is empty forever** on this line, which is what makes
`Inert` a real state (never initialise) instead of an override answering false. `initInternal()`'s own three
instructions are `aload_0; invokevirtual gatherCapabilities; return` — pinning them is pinning the eager path.

## The routes, and why five of them are worse

- **A. RELAX THE PROOF: emit a certificate whose `protocol()` half is "the transform ran".** Refused. It is the shim
  the task forbids, and it is worse than refusing: the manifest (`META-INF/forbric/required-ancestor-compositions.tsv`)
  exists precisely so a stateful ancestor cannot disappear silently. A proof that asserts nothing makes
  `RequiredAncestorCompositions.verify` decorative, and the next real regression in the carrier would define broken
  classes with a clean log.
- **B. SYNTHESISE 1.21.1 ANALOGUES OF `$Entities/$BlockEntities/$Levels` (one subclass of the carrier per root) AND
  KEEP `protocol()` AS IS.** Refused. Each such class would carry a **second copy** of the carrier's eight fields, and
  the event key would be the *subclass's* `Class`, not the owner's — so `AttachCapabilitiesEvent<Entity>` would only
  be constructed correctly if the subclass hard-coded it, which is rebuilding the 26.2 model out of a line that
  deliberately deleted its hook. `gatherCapabilities()` being `final` means there is no seam to build it from.
- **C. REUSE ONE DELEGATE (e.g. `Entities`) FOR ALL THREE ROOTS.** Refused, and this one is not cosmetic: `baseClass`
  would be `Entity.class` for a `Level`, so every `AttachCapabilitiesEvent<Level>` listener would silently never fire.
  A type error in the single argument the whole model now depends on, and no compiler would see it.
- **D. PORT THE RUNTIME HALF ONLY, LEAVING THE CERTIFICATE NULL (the previous round's refusal, restated).** Refused
  again, same reason: a class that compiles and that nothing constructs. The count falls; the blocker stays.
- **E. DO NOTHING (the previous round's choice).** Untenable now, and in a different way than before: it was the right
  call when the shape was unknown. The shape is measured, and leaving it means every later stage reports its count
  against a base that cannot be defined.
- **F. A SECOND CERTIFICATE SHAPE, SELECTED BY THE MANIFEST'S OWN `sourceSuperclass` (chosen).** No property, no
  version string: the manifest already says which class the merge dropped, so it already says which shape applies.
  A `removed` naming a `$`-nested class is 26.2's shape; a `removed` that **is** the carrier is this line's.

## What the 1.21.1 certificate has to prove (the obligations, named before they are coded)

P1. **The removed class is the root's actual source superclass** — implied by the manifest row and enforced by
    `Certificate.proves` (`removed.equals(r.sourceSuperclass())`).
P2. **The carrier's superclass is `java/lang/Object` and its field set is exactly the pinned one**, so delegating to
    it loses nothing: on 26.2 this check was `fields.isEmpty()` on a subclass; on 1.21.1 the state is *in* the removed
    class and the delegate inherits it, so "no unaccounted state" becomes "the inherited state is exactly this".
P3. **The carrier's `<init>(Class)` and `<init>(Class, boolean)` token streams are the pinned ones** — the second pins
    the field initialisation order and `isLazy = SUPPORTS_LAZY_CAPABILITIES && eager`.
P4. **`AsField` extends the removed class, declares exactly `owner`, and its `(Class, B)` constructor / `initInternal`
    / `serializeInternal` / `deserializeInternal` are the pinned token streams** — those are the four access points
    the composition calls, and `initInternal`'s body is the eager gather.
P5. **`doGatherCapabilities`'s token stream is the pinned one**, proving the event key is the `Class` argument.
    Without this the "one provider, three roots" step would be an inference; with it, it is a proof.
P6. **The delegate for THIS root exists, chains `$<Root> extends $Composed extends $AsField`, and its constructor
    passes the pinned `Class` literal** — `ldc Entity.class` / `BlockEntity.class` / `Level.class`. That is the exact
    replacement for 26.2's per-root provider class: the per-root thing is now a constant, and the certificate pins it.
P7. **The carrier declares no abstract method**, so there is no override site to drop (contrast 26.2, where the two
    `protected abstract` hooks *are* the contract).

## What this stage does NOT decide, and says so before coding

The composition's **dispatch** half (the `ForgeCaps` save/load funnels, `ServerLevel.initCapabilities`,
`LevelChunk.capProvider`, the lost field initializers) is a different question from the **definition** blocker, and
its anchors are different classes on this line. It is ported where a 1.21.1 anchor exists and stands down — with its
existing warning, which names the anchor — where it does not. Every stand-down is listed by name in the verification
section; none of them is a silent pass, and none of them is blamed on the certificate.

The previous round measured that porting the runtime half alone removes **29** errors from
`KernelForgeCapabilities.java` (14 axis-2 + 6 axis-1 + 9 cascades). This stage does not chase those: they fall out of
doing the work honestly, in the other order — the certificate is written first and the runtime half is written to the
shape the certificate can prove. If the 29 fall, that is reported as a consequence.

## The port

Two files carry the decision, and one new file is the runtime half. Nothing is stubbed, and the three places that
could have been faked are named in the code.

### 1. `ForgeCapabilityProtocol` — two shapes, selected by the manifest

`protocol(removed, owner, reader)` now dispatches on the row it was handed:

```
BASE.equals(removed)  ->  selfProvider(...)     // 1.21.1: the removed class IS the carrier
else                  ->  nestedProvider(...)   // 26.2: the removed class is a $nested subclass
```

`nestedProvider` is the previous body, **moved and not otherwise touched** — same pinned token lists, same
`fireAttachCapabilitiesEvent` comparison, same "no additional source state" sweep. `selfProvider` is new and is the
obligations P1–P7 written as checks:

| check | what it pins, in tokens |
|---|---|
| carrier super | `java/lang/Object` |
| carrier state | the nine fields, `access:name:desc`, in declaration order — `SUPPORTS_LAZY_CAPABILITIES`, `baseClass`, `capabilities`, `valid`, `isLazy`, `lazyParentSupplier`, `lazyData`, `registryAccess`, `initialized` |
| carrier constructors | `<init>(Class)` and the eleven-store `<init>(Class, boolean)`, the second of which is where `isLazy = SUPPORTS_LAZY_CAPABILITIES && eager` lives |
| **the event key** | `doGatherCapabilities`: `getfield baseClass`, `getProvider()`, `ForgeEventFactory.gatherCapabilities(Class, ICapabilityProvider, ICapabilityProvider)`, `putfield capabilities`, `initialized = true` |
| carrier has no hooks | no `ACC_ABSTRACT` member — so nothing is being overridden away |
| `AsField` | `super = carrier`, exactly `owner`, `<init>(Class, B)` = `[v25:0, v25:1, carrier.<init>(Class), v25:0, v25:2, putfield owner, return]`, and `initInternal`/`serializeInternal`/`deserializeInternal` bodies |
| the delegate | `$<Kind> extends $Composed extends $AsField`, `$Composed.<init>(Class, Object)` = `[aload0, aload1, aload2, checkcast ICapabilityProviderImpl, invokespecial AsField.<init>(Class, B), return]`, and `dispatcher()` |
| **the per-root key** | the delegate's own constructor: `[aload0, ldc <Root>.class, aload1, invokespecial Composed.<init>(Class, Object), return]` — the Class literal, pinned |
| the factory | `KernelForgeCapabilities.create`: `aload0, invokevirtual AsField.initInternal, aload0, areturn` |
| the wiring | `KernelForgeCapabilities.entity/blockEntity/level`: one `ifnull`, one delegate, one `create` — so a root wired to another root's delegate fails |

`Certificate` grew one component, `accessorHelper`, and one check beside the existing field/delegate/seam checks: the
final definition's own `forbric$caps()` must reach the factory this certificate was issued for. It is `null` on the
nested shape (26.2 has no such link to pin) and it is `inert` when dispatch is off — so the switch itself is certified
rather than skipped.

**Two changes to shared machinery, both justified in place:**

- `token()` learned loadable constants: `c:<descriptor>`. Without it a `Class` literal is indistinguishable from any
  other `ldc` (`o18`), and P6 could not exist. The opcode is deliberately **not** in the token: `ldc` and `ldc_w` are
  the same constant and which one javac emits depends on the constant-pool index, i.e. on unrelated edits.
  None of 26.2's four pinned token lists contains an `ldc`, so nothing on that line changes — checked by the 26.2
  capability suite (below), not by inspection alone.
- `certificate(...)` takes `dispatch`, because the accessor's factory is where the switch shows up on this line.

### 2. `ForgeCapabilityCompositionTransformer` — one composition, a line's worth of differences

`compose()` is unchanged except for **one omission**: `serializeCaps(ValueOutput)` is not emitted on the SELF shape,
because `ValueInput`/`ValueOutput` do not exist on this line. Everything else the composition adds — the interface,
the field, the accessor, `getCapability`, `invalidateCaps`, `reviveCaps`, `gatherCapabilities`, `getCapabilities`,
`serializeCaps(HolderLookup.Provider)`, `deserializeCaps(HolderLookup.Provider, CompoundTag)` — has the same name,
descriptor and bytecode on both lines, so the accessor and seven of the eight delegates are literally the same
emission. That is worth stating because it is the strongest evidence that the per-root difference really did collapse
to one argument: **26.2's composed Entity and 1.21.1's composed Entity differ by exactly the class of one method.**

The dispatch half is where the two lines part, and each part is anchored on something that was verified:

- **`CompoundTag` save/load seam** (previous round's item 3). New: `saveBlockEntity`/`loadBlockEntity` on
  `saveAdditional/loadAdditional(CompoundTag, HolderLookup.Provider)` and `saveEntity`/`loadEntity` on
  `saveWithoutId(CompoundTag)`/`load(CompoundTag)`. `saveWithoutId` returns `CompoundTag`, so its funnel counts
  `ARETURN` and inserts **above** the return value — stack-neutral there, and no instruction has to be found relative
  to it. Each funnel raises `maxStack` to what the four pushes need.
- **`ServerLevel.initCapabilities`.** 26.2's anchor, `LevelAttachmentsSavedData.init`, is a NeoForge class that does
  not exist here. Measured: the method **survived** the merge on this base (it is declared, and it still calls
  `gatherCapabilities`, `getDataStorage` and `getCapabilities`); only Forge's call at the constructor's end was lost
  with the superclass. So the port restores the call site and nothing else. A first draft synthesised
  `initCapabilities()` as well; the measurement says that half is not needed on this base, so the synthesis was
  **removed** rather than shipped as code no run exercises.
- **`LevelChunk.capProvider`.** 26.2 anchors on a `PUTFIELD` of `unsavedListener`; that field does not exist on this
  line. The final field *did* survive with nothing writing it (`javap`: one declaration, zero stores). The 1.21.1
  anchor is the constructor's own `super(...)` call — the one statement that is certainly there and certainly
  precedes a legal write to a final field — and `initInternal()` goes before the constructor's single `RETURN`, which
  is where Forge put it. A first draft counted *any* `INVOKESPECIAL <init>` as the super call and bailed out because
  this constructor also allocates `Heightmap`s and sections; the anchor is now `owner == node.superName`.
- **Unchanged and working on both lines, measured rather than assumed:** `Entity.remove → invalidateCaps` and
  `Entity.revive → reviveCaps` already appear in the merged 1.21.1 base (so `insertAfterCall` stands down on its
  "already there" branch), `BlockEntity.setRemoved` calls NeoForge's `invalidateCapabilities()` once and gets the
  Forge call after it, and `replayLostInitializer` needs only `reviveCaps()` — which this line has
  (`LivingEntity.reviveCaps` = `[aload0, invokespecial Entity.reviveCaps, aload0, aload0, invokestatic
  EntityEquipmentInvWrapper.create, putfield handlers, return]`, a straight line starting `ALOAD 0`).

### 3. `src/runtime/mc-line/1.21.1/java/…/KernelForgeCapabilities.java` — the runtime half

A 23rd overlay file, replacing the shared one for this line only (the 26.2 file is untouched). `Composed` forwards the
root's `Class` to `AsField`; `Entities`/`BlockEntities`/`Levels` differ **only** in that literal; `Inert` is not an
override but the absence of `initInternal()`; the factories are unchanged in name and descriptor, so the synthesised
accessor is byte-identical across lines.

Two behaviours are stated in the code because they differ from 26.2 and both are load-bearing:

- `Inert` is a **state**: `AsField(Class, B)` reaches `CapabilityProvider(Class, false)`, so `isLazy` is false and
  `capabilities` stays null until someone calls `initInternal()`. `getCapability` therefore answers
  `LazyOptional.empty()` forever, `serializeCaps` returns null and `deserializeCaps` is a no-op — the same end state
  26.2 reaches by marking an eager provider initialised with no dispatcher, arrived at from the other side.
- `injectCapabilities` is an **instance** API here: `CapabilityManager.injectCapabilities(ModList)` and
  `ModList.get().getAllScanData()`. Same change stage 2 made in `KernelForgeDeclarationReaders`.

**The overlay compiles on its own, against the real carriers** — that is not a convenience, it is what makes the
certificate a test of real bytes:

```

                       build/classes/java/main ; forgespi-7.1.5 ; asm-9.10.1>
  -> 6 class files: KernelForgeCapabilities{, $Composed, $Entities, $BlockEntities, $Levels, $Inert}
```

### 4. The proof: `ForgeCapabilityComposition1211Test`

Where the acceptance criterion now lives. It reads the real 1.21.1 merged base and the real 1.21.1 carrier, composes
the three roots, and calls the **same** method `ForbricClassLoader.define` calls:

```java

contracts.register(new ForgeCapabilityCompositionTransformer(reader));
contracts.verify("net.minecraft.world.entity.Entity", emitted, reader);   // no LinkageError
```

and, as the control, the same call against a loader with **no** proof registered, which must throw. Both directions
are asserted for all three roots, so the test cannot pass by `verify` becoming a no-op.

It also asserts that the row this subsystem does **not** cover is not silently claimed: the base's fourth row,
`EnderDragonPart`, must still be refused by the loader after the capability proof is registered, because that is
`PartEntity`'s composition and nothing here touches it.

Four adversarial controls, each a one-line lie about one input:

| lie | must be refused because |
|---|---|
| `$Levels.class` replaced by `$Entities.class` | the Class literal is the per-root key; a `Level` composed from the Entity delegate posts a `Level` to `AttachCapabilitiesEvent<Entity>` and loses every listener |
| a `NOP` inserted into `doGatherCapabilities` | same meaning, different bytecode: the proof is a fingerprint, and P5 is what makes "one provider, three roots" a proof instead of an inference |
| a field added to the carrier | unknown inherited state cannot be dismissed because the delegates still compile |
| `initInternal()` emptied to a bare `RETURN` | it *is* the eager gather on this line |

and one non-adversarial one: a definition with the composed field removed must still be refused, which is what keeps
the certificate about the artifact and not about the transform having run.

## What is still not verified, stated plainly

- **No 1.21.1 kernel jar has ever been built and no 1.21.1 launch has been attempted.** A certificate that verifies
  is a proof about bytes, not a game. Nothing in this stage — or any stage before it — has executed on 1.21.1.
- **The overlay's six class files have never been loaded by a JVM as part of a kernel.** They were compiled against
  the real carriers and they are what the certificate fingerprints, which is why the proof is about real bytes; that
  is the whole of it.
- **The certificate is proved by a test that calls `RequiredAncestorCompositions.verify` directly**, not inside
