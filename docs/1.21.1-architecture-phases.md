# The four architecture phases, and the one acceptance that is a loss

Decision taken at round 256, from a direct instruction to split the 84 pipeline errors into independent
architecture phases rather than compile them out. This file is the contract for those four phases. Each
phase is independent: it can be started, measured, and reverted without touching the other three.

    state at the decision point   TOTAL 152   axis1 73 / axis2 73 / axis3 0 / cascades 6
    measurement                   measure.sh under M2, transcript md5 recorded per run

Shared acceptance line for every phase, unchanged from stages 1-28:

    target axis DOWN, axis1 and axis3 byte-identical, cascades NOT UP

A rise in axis1 or axis3 means the change moved errors between buckets instead of removing them, and is a
failure regardless of the total.

## The one accepted loss: Hud, 5 errors

26.2's net.minecraft.client.gui.Hud carries **64 private fields** (measured, javap -p). There is no shape
to reproduce and no extraction path that does not amount to writing a second HUD. These 5 errors are
accepted as lost. They stay in the count and the count is not claimed to be zero.

## Phase A -- pip, 31 errors

    26.2 types (all absent from 1.21.1, measured zero entries):
        net.minecraft.client.gui.render.pip.PictureInPictureRenderer        abstract class, 3 private fields, 6 methods
        net.minecraft.client.renderer.state.gui.pip.PictureInPictureRenderState   interface, 0 private fields, 10 methods
        net.neoforged.neoforge.client.gui.PictureInPictureRendererRegistration    record, 2 private fields, 7 methods
        net.neoforged.neoforge.event.RegisterPictureInPictureRendererEvent

    1.21.1 has:  GuiGraphics, BlockEntityWithoutLevelRenderer   (both present)
    1.21.1 lacks: the whole pip framework -- render/pip has zero entries

The 26.x pip framework renders a 3D thing into a rectangular region of a GUI. 1.21.1 can do that with
GuiGraphics pose plus a BlockEntityWithoutLevelRenderer, which is how 1.21.1 vanilla draws 3D items, but
there is no framework to hook: no registry, no render state, no bake step. So this phase is not a rename
and not a compat class. It is:

    A.1  decide the 1.21.1 extension point: a Forbric-owned registry of "draw this region with this
         renderer", driven from wherever the merged base currently asks the pip framework.
    A.2  implement the registry and one renderer that draws through GuiGraphics + BlockEntityWithoutLevelRenderer.
    A.3  bridge: a 26.x-shaped PictureInPictureRenderer/Registration on top, so the kernel's existing call
         sites keep their names.

    A.4  accept when axis1 and axis3 are unchanged and TOTAL drops by the 31.

CHEAPEST FIRST ACTION. Do not start at A.1. First run the shape probe the same way stage 28 did: take the
31 error sites, list exactly which members of the four types they touch. In the two phases that succeeded
in stage 28 the call sites used ONE member out of a large type. If pip is the same, A.2 shrinks to one
renderer. That probe is a single scripted javap pass and it decides whether this phase is a week or a month.

## Phase B -- class transformation, 21 errors

    net.neoforged.fml.classloading.transformation.{ClassProcessorSet,ClassTransformer,TransformingClassLoader}
    net.neoforged.fml.loading.mixin.FMLMixinClassProcessor
    net.neoforged.neoforgespi.transformation.{ClassProcessor,ClassProcessorIds,ProcessorName}

    measured: FMLMixinClassProcessor, ClassProcessor, ProcessorName, ClassProcessorSet -- all zero on 1.21.1
    1.21.1 has: cpw.mods.modlauncher.api.ITransformer, ITransformationService, ITransformerVotingContext,
                TransformingClassLoader, ClassTransformer

THIS PHASE HAS A DESIGN DECISION BEFORE ANY CODE, and it is the same kind of decision stage 1.1 demanded.
KernelFmlTransformerView (180 lines) does not bridge a capability. It builds a FAKE OBJECT GRAPH -- "exactly
that path and nothing beside it" -- so that one mod's mixin plugin (libjf_unsafe_v0) can walk
TransformingClassLoader -> classTransformer -> processors -> processors.get(ClassProcessorIds.MIXIN) ->
FMLMixinClassProcessor.transformer and wrap that in its own AsmTransformer.

    B.1  read libjf_unsafe_v0's mixin plugin and answer: on 1.21.1, does it need that walk to succeed, or
         does it take a different path when the classes are absent? This has never been read. Until it is,
         "excluding this phase loses nothing on 1.21.1" is an UNVERIFIED claim and must not be acted on.
    B.2  if the walk is needed: build the same graph against 1.21.1's real ModLauncher classes, and then
         the transformer's descriptor match has to be re-derived per line, because the merged base's
         onResourceReload descriptor differs between lines (stage 8).
    B.3  if the walk is not needed: exclude KernelFmlTransformerView from the 1.21.1 source set and record
         that libjf takes a different path there.

    B.4  accept when TOTAL drops by 21 AND B.1's answer is written down with evidence.

## Phase C -- tooltips, 18 errors

    net.neoforged.neoforge.common.tooltip.{TooltipAppender,TooltipLocation,ItemTooltipHandler}
    net.minecraft.world.item.component.TooltipDisplay                          (vanilla 26.x, NOT on 1.21.1)
    net.neoforged.neoforge.event.RegisterTooltipAppendersEvent

    measured on 1.21.1:  TooltipProvider present but WITHOUT the nested TooltipContext
                         DataComponentType present
                         TooltipFlag present
                         TooltipDisplay ABSENT  (the component tooltip system is 1.21.2+)
    shapes on 26.2:      TooltipAppender interface, 1 method
                         TooltipLocation enum, 4 constants (HEAD, POST_CUSTOM, PRE_ITEM_INFO, TAIL)
                         TooltipDisplay record, 3 private fields
                         ItemTooltipHandler class -- the ordering pipeline, private static lists

    C.1  TooltipAppender and TooltipLocation are reproducible for near-zero cost: an interface with one
         method and an enum with four constants. Do them, with the stage-28 discipline (compat package,
         Forbric prefix on the name, two table rows, measure).
    C.2  TooltipDisplay has to be DESIGNED, not copied: its job is per-item "hide these lines" flags. On
         1.21.1 there is no component-based tooltip so nothing consumes those flags. Decide whether to
         reproduce the flag semantics or to carry the record as a value object with no consumer, and write
         down which -- a value object with no consumer is a stub, and stubs are forbidden by the objective.
    C.3  ItemTooltipHandler is the pipeline. It is why the kernel file is 223 lines. Its 1.21.1 edition
         means reimplementing appender ordering on top of ItemTooltipEvent, and the observable order a mod
         sees will differ from 26.2's. That difference has to be recorded, not smoothed over.

    C.4  accept when TOTAL drops by 18 and the C.2 decision and the C.3 difference are both written down.

NOTE ON WHAT THIS PHASE PRESERVES. TooltipAppender does not exist in NeoForge 1.21.1, so no 1.21.1 mod can
use it. What phase C preserves is Forbric's own Fabric-to-NeoForge tooltip bridge: Fabric's tooltip
ordering hooks stop working without it. It is not mod compatibility and should not be sold as such.

## Phase D -- FuelValues, 14 errors

    net.minecraft.world.level.block.entity.FuelValues                         (vanilla 26.x, NOT on 1.21.1)
    kernel user: KernelFabricFuel, 29 sites

    measured on 1.21.1:  AbstractFurnaceBlockEntity.getFuel(): Map<Item,Integer>
                         AbstractFurnaceBlockEntity.isFuel(ItemStack)
                         NO FuelValues, NO Builder, NO DataMapHooks.populateFuelValues

    shapes on 26.2:      FuelValues class, 1 private field, 9 methods, has Builder + vanillaBurnTimes

WHAT THE KERNEL ACTUALLY DOES, and why "the data maps cleanly" was wrong: it does not read the fuel map.
It attaches to a BUILDER pipeline -- populateFuelValues hands it a builder, it adds entries, then build().
1.21.1 has no such pipeline.

    D.1  decide the 1.21.1 extension point: a Forbric fuel table built at datapack load, reachable where
         1.21.1's furnace asks for fuel. 1.21.1's getFuel() is a static map built from vanilla's list, so
         either it is rebuilt on reload or a lookup is interposed.
    D.2  implement that table and wire Fabric's fuel additions into it, which is the actual purpose of
         KernelFabricFuel (a Fabric mod's fuel never went into a furnace on the merged server).
    D.3  bridge: a 26.x-shaped FuelValues/Builder on top so the kernel's 29 sites keep their names.

    D.4  accept when TOTAL drops by 14, axis1/axis3 unchanged, and a reload rebuilding the table is
         demonstrated or explicitly recorded as not demonstrated.

## The per-site remainder, about 63 errors

Not part of these four phases. Every file with exactly one missing type has been assessed:
InteractionInformation (done, 872337f), ForgeLayer (done, 5931a24), ListenerKey and UnbakedModelParser
(descriptor-bound), VanillaClient/ServerListeners (private static data table that javap cannot reveal).
The rest are individually diagnosed in stage 27 and stage 28 and none of them is a rename.

## What is NOT in this plan

The kernel jar and the launch. Both are in stage 6 of the objective and both are blocked on TOTAL
reaching 0, which the four phases above do not reach: 31+21+18+14 = 84, leaving 152-84 = 68. Reaching zero
also requires the per-site remainder and the 5 Hud errors, and the 5 Hud errors are an accepted loss.

So this plan does not end in a jar. It ends at 68, or lower if the per-site remainder shrinks. That has to
be said at the start rather than discovered at the end.
