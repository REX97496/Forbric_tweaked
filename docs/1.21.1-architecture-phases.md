# The four architecture phases, and the one acceptance that is a loss

Decision taken at round 256, from a direct instruction to split the 84 pipeline errors into independent
architecture phases rather than compile them out. This file is the contract for those four phases. Each
phase is independent: it can be started, measured, and reverted without touching the other three.

    state at the decision point   TOTAL 152   axis1 73 / axis2 73 / axis3 0 / cascades 6
    measurement                   measure.sh under M2, transcript md5 recorded per run

Shared acceptance line for every phase, unchanged from stages 1-28:

    target axis DOWN, axis1 and axis3 byte-identical, cascades NOT UP

A rise in axis1 or axis3 means the change moved errors between buckets instead of removing them, and is a
failure regardless of the total.

## The one accepted loss: Hud, 5 errors

26.2's net.minecraft.client.gui.Hud carries **64 private fields** (measured, javap -p). There is no shape
to reproduce and no extraction path that does not amount to writing a second HUD. These 5 errors are
accepted as lost. They stay in the count and the count is not claimed to be zero.

         renderer", driven from wherever the merged base currently asks the pip framework.

CHEAPEST FIRST ACTION. Do not start at A.1. First run the shape probe the same way stage 28 did: take the
31 error sites, list exactly which members of the four types they touch. In the two phases that succeeded
in stage 28 the call sites used ONE member out of a large type. If pip is the same, A.2 shrinks to one
renderer. That probe is a single scripted javap pass and it decides whether this phase is a week or a month.

D.2  the real work: subscribe FurnaceFuelBurnTimeEvent and answer from the Fabric-registered table, which is
     the actual job of KernelFabricFuel -- a Fabric mod's fuel never reached a furnace on the merged server.

D.3  bridge: the 26.x-shaped Builder on top of the value object, so the kernel's existing call sites keep

D.4  accept when TOTAL drops by 14, axis1 and axis3 unchanged, and the event subscription is either

# Phase B: the LibJF source was read, and it settles the question (round 273)

The contract said phase B must not be touched until libjf_unsafe_v0's mixin plugin had been read, because
"1.21.1 does not need that impersonation" was an unverified claim. The mod is not in this workspace (only a
`libjf-translate-v1.neoforge.mods.toml` test fixture exists), so it was fetched from upstream:

    https://git.jfronny.dev/JfMods/LibJF/src/commit/44f844afe2cba23ebf38787d78e09c271a4de66d/
        libjf-unsafe-v0/src/main/java/io/gitlab/jfronny/libjf/unsafe/MixinPlugin.java

## What onLoad actually does

    public void onLoad(String mixinPackage) {
        try {
            TransformingClassLoader cl = (TransformingClassLoader) Thread.currentThread().getContextClassLoader();
            Field f1 = TransformingClassLoader.class.getDeclaredField("classTransformer");
            Field f2 = ClassTransformer.class.getDeclaredField("pluginHandler");
            LaunchPluginHandler ph = (LaunchPluginHandler) f2.get(ct);
            FMLMixinLaunchPlugin plugin = (FMLMixinLaunchPlugin) ph.get("fml-mixin").orElseThrow(...);
            Field f3 = FMLMixinLaunchPlugin.class.getDeclaredField("transformer");
            AsmTransformer.INSTANCE.delegate = (IMixinTransformer) f3.get(plugin);
            f3.set(plugin, AsmTransformer.INSTANCE);
        } catch (Throwable e) {
            LibJf.LOGGER.error("Could not initialize LibJF ASM", e);
        }
    }

Every other method of the plugin is inert: shouldApplyMixin returns **false**, getMixins returns **null**,
preApply and postApply are empty, getRefMapperConfig returns null. So the plugin does no mixin applying at
all -- its entire purpose is the ASM hook install above.

## The answer, and it is decisive

THE WHOLE INSTALL IS WRAPPED IN catch (Throwable). A ClassCastException, a NoClassDefFoundError, a
NoSuchFieldException -- all of them are swallowed, one log line is written, and LibJF continues loading.

So on 1.21.1, where TransformingClassLoader does not exist, this plugin fails SOFTLY. Excluding
KernelFmlTransformerView therefore does not break LibJF and does not crash anything. The behavioural cost is
exactly:

    LibJF's ASM patches do not apply on 1.21.1, and LibJF logs "Could not initialize LibJF ASM".

That is one optional feature of one mod not working, self-reported. It is not a crash and not a silent
corruption.

## A second finding: the kernel comment describes a DIFFERENT LibJF version

KernelFmlTransformerView's own comment says the walk is
`classTransformer -> processors -> processors.get(ClassProcessorIds.MIXIN) -> FMLMixinClassProcessor.transformer`.
The upstream source at 44f844a walks
`classTransformer -> pluginHandler -> pluginHandler.get("fml-mixin") -> FMLMixinLaunchPlugin.transformer`.

Those are different object graphs. So the 180 lines of impersonation were written against a different LibJF
build than the one that was read. That does not make them wrong for the build they targeted, but it does mean
they cannot be validated from this source, and it further weakens the case for carrying them onto a line
where the real classes are absent anyway.

## So B.1 is decided

    decision   EXCLUDE KernelFmlTransformerView from the 1.21.1 source set
    evidence   the upstream plugin is fail-soft on Throwable, so absence costs a logged error, not a crash
    not done   the actual exclusion mechanism, which has not been found yet: normalizeRuntimeJava rewrites
               files in src/runtime/java but has no exclude step. A Gradle-side source-set or per-line
               exclusion has to be found or added, and that is the next step.

The claim in earlier stages that "excluding this phase loses nothing on 1.21.1" is now upgraded from
UNVERIFIED to VERIFIED-WITH-A-COST, and the cost is written down rather than waved away.

The two edits that were tried, so the next attempt does not start from nothing:

    1. the signature's TooltipDisplay became net.forbric.compat.tooltip.ForbricTooltips.Display
    2. the constructor call dropped its sixth argument:
         new ItemTooltipEvent(stack, player, tooltip, flag, context, display)
       became
         new ItemTooltipEvent(stack, player, tooltip, flag, context)
       because 1.21.1's ItemTooltipEvent takes five arguments and 26.2's takes six.

Whoever retries it should read all 98 lines and count the uses of the display argument before assuming two.

# Why 26.2 and 1.21.1 can disagree on a CONSTRUCTOR'S ARITY

This is the first case in the port of a type whose constructor takes a different NUMBER of arguments on the
two lines, and it matters because it rules out the usual compat trick. A compat subclass cannot fix it: its
super(...) call has to be valid on both lines, and six arguments are only valid on one. So arity differences
need either an overlay or a per-line factory, and neither is a table row.

# Round 315: the chained-call scan, and what it actually found

Round 314 found that recipe.id().identifier() becomes recipe.id().location() after the rename table, and that
ResourceLocation has no location() -- because on 26.2 id() returns a ResourceKey and .identifier() unwraps it,
while on 1.21.1 id() returns the ResourceLocation directly. That raised a question the port had never asked:
does a rename rule stay correct when it fires on a CHAINED call, where the receiver's type may differ between
lines?

The scan: 120 non-overlaid files x 85 rules, matching only the chained form (a word character, a dot, then the
token). 29 of the 85 rules match in that position. Of those 29:

    28 are benign.  Either a type RENAME (Identifier, EntitySpawnReason, EntityTypes, AbstractBoat,
    ContainerStorage, ...), where rewriting a type name at a chained position is exactly right, or a match
    inside one of the compat classes' own javadoc (FuelValues, TooltipDisplay, PictureInPictureRenderer,
    ClassProcessorSet, FluidModel, UnbakedModelParser, ...), which is cosmetic.

    1 is a real hazard: identifier() firing in KernelNeoRegistries.

Together with the KernelRecipeSync case from round 314, that makes two places, not a class of problem. So TSV
correctness does NOT need a new checking dimension -- it needs human judgement on two call sites. That removes
a risk this document had started to assume was systemic.

## A side effect worth recording, because it is self-inflicted

Seven of the eight compat class files have rename-rule tokens inside their own javadoc, so normalizeRuntimeJava
rewrites their documentation too. The classes still compile and behave correctly -- the earlier invariant check
confirmed that the class NAMES are safe, which was the point of the Forbric prefix -- but the prose no longer
says what it said. ForbricUnbakedModelParser's javadoc, for instance, now reads as if it were describing itself.

That is not a functional defect. It is a documentation defect in documents whose entire purpose is to record
things accurately, which is why it is written down here rather than left to be noticed.

# Round 325: "packaged into a record" is a PATTERN, not eight separate errors

Three of the remaining error groups are the same shape, and until this round they were being handled one at a
time. 26.2 packages a tuple of raw fields into a record with a getter; 1.21.1 keeps the raw fields.

    KeyEvent         26.2  InputEvent$Key(KeyEvent, int) + getKeyEvent(): KeyEvent
                     1.21.1  InputEvent$Key(int, int, int, int), no getKeyEvent
                     kernel calls it five times, in a file with nine unique rules

    MouseButtonInfo  26.2  InputEvent$MouseButton$Pre(MouseButtonInfo, int) + getMouseButtonEvent()
                     1.21.1  InputEvent$MouseButton$Pre(int, int, int), no getMouseButtonEvent
                     kernel calls it once, to build a Forge event

    VanillaResult    26.2  AnvilUpdateEvent.getVanillaResult(): VanillaResult
                     1.21.1  AnvilUpdateEvent has no such thing, and no record of what it was built with
                     kernel calls it three times

THE FIRST TWO ARE FIXABLE AND THE SAME WAY: rebuild the caller's arguments from the raw fields instead of passing
the packaged object. getKeyEvent() becomes getKey(), getScanCode(), getAction(), getModifiers(); getMouseButtonEvent()
becomes getButton() and getModifiers(). Six errors, one shape, one method of repair.

THE THIRD IS NOT FIXABLE THE SAME WAY, and the reason is the useful part: VanillaResult's job on 26.2 is to
remember what the event looked like BEFORE anything modified it. 1.21.1's event does not remember that, so a compat
VanillaResult could only read the CURRENT values and the kernel's untouched comparison at :254 would become a
comparison of the event with itself -- always true, and silently so. So "packaged record" splits into two classes
depending on whether the record carries data the line still HAS (recoverable) or data the line never KEPT
(not recoverable).

Six of the remaining errors are in the recoverable class and have a settled repair. Three are in the
non-recoverable class and need the caller to snapshot values before the event is posted -- which is a code change
in a 13-rule file, not a substitution.

Not done: fixing the six needs two overlays (nine unique rules and two), and this session no longer has the room
to complete one and verify it on both lines. The specification for the larger one is already in this document.

# Rounds 340-342: one more error back, and a limit of overlays that is worth knowing

## Round 340: the same IContext fix in a second file, 53 -> 52

KernelModifiableDataViews had the identical problem as KernelForgeConditions -- an anonymous
net.minecraftforge...ICondition.IContext implementing only getTag, which 1.21.1's interface makes insufficient.
The overlay adds getAllTags delegating to the wrapped source. That file hits ZERO rename rules, so the overlay
needed no rule translation and no row deletion.

It took three attempts because I inserted with regex re-concatenation instead of by line. The first emitted
"}@Override" on one line; the second left a stray closing brace because the regex ended at the method's own
brace. Both manifested as eight syntax errors, and both times my grep for TOTAL found nothing.

What broke the loop was the harness saying, verbatim:

    REFUSING TO SPLIT ... 8 error blocks but no `symbol:` line and no `does not exist` in the whole transcript

That sentence distinguishes a SYNTAX error from a SYMBOL error, and it is the only place in this tooling that
says so. Reading it as "look at the braces, not the types" saved a round. Every future failure with this shape
should be read that way first.

Durable lesson: insert into brace-structured text by LINE, never by re-concatenating a regex match. Four of this
run's PowerShell-string mistakes have been of the re-concatenation kind and none of the line-based ones failed.

## Round 342: KernelGameBlockEvents cannot be fixed in an overlay, and the reason is structural

The remaining error is real and diagnosable. 26.2 names NeoForge's event BreakBlockEvent (a top-level class);
1.21.1 names it net.neoforged.neoforge.event.level.BlockEvent$BreakEvent. The table rewrites BreakBlockEvent to
the bare simple name BlockEvent.BreakEvent -- and the kernel ALSO uses MinecraftForge's
BlockEvent$BreakEvent, written out literally, in the same file. The two have the same simple name on 1.21.1 and
different packages, so the bare rewrite resolves against whichever BlockEvent is imported, which is Forge's.

So the rewrite is right in direction and wrong in spelling, and there are two obvious repairs:

    change the row's TARGET to the NeoForge fully-qualified name    -> the import line becomes a nested-class
        import, and then the file's LITERAL BlockEvent.BreakEvent uses bind to NeoForge's instead of Forge's, so
        the Forge side breaks in exchange
    change the shared source to spell both sides out                -> touches src/runtime/java and therefore the
        26.2 build, which is off limits without a full 26.2 re-verification

And it cannot be repaired in the overlay at all, for a reason that generalises:

    AN OVERLAY CONTAINS POST-RULE TEXT. When a rule maps A to B and the file already contains B literally, the
    overlay can no longer tell which B came from A. Here BreakBlockEvent (NeoForge) and BlockEvent.BreakEvent
    (Forge) are BYTE-IDENTICAL after rewriting.

I tried qualifying both sides and measured: still 52, with the Forge side now wrong as well. Reverted.

So this is a fifth kind of defect, distinct from the four already recorded: not a name that is mutually exclusive,
not a receiver whose level differs, not a redundant row, not a row wrong in one place and right in another -- but a
row whose TARGET collides with a name the file already uses. It is unfixable from the overlay layer by
construction, and it stays as one error.
